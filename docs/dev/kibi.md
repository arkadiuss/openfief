# Requirements with kibi

[kibi](https://github.com/Looted/kibi) (by pfranczyk) holds the requirements: requirements, scenarios, tests, facts and code links in `.kb/`, checked by Prolog and exposed to agents over MCP. DESIGN.md says why; kibi says what, and enforces it. Requirements cite DESIGN.md's GR and D IDs.

## Rules

- **Never edit `.kb/` by hand.** Write only through kibi's tools. kibi never commits; stage and commit its files with your change.
- **Before changing behavior,** search kibi for the requirements that govern it and respect their firmness:
  - `firm` means the author stated it: ask before changing it, and change it only through `supersedes` with a reason.
  - `default` and `exploratory` may be revisited on evidence.
- **New behavior** gets a modeled requirement with a scenario, before or with the code. Each behavioral function is owned by a kibi `symbol` that `implements` the requirement and is `covered_by` the test that verifies its scenario. `// implements` comments are not the record.
- **Decisions and open questions:** a requirement imported from DESIGN.md is `firm` and cites the item, such as `design-decisions:D-18#2`. Open questions are observation facts tagged `review:open-question`. Proposals stay in docs/proposals/ until the author decides them.
- **Blocked commit:** the pre-commit gate blocks unowned or uncovered behavioral symbols. Fix the cause with kibi's own `kibi-commit-review` skill; never bypass the hook.
- **Learn the workflow on demand** from kibi's bundled skills (`kibi-usage`, `kibi-commit-review`). Don't preload them.
- **Before handing work back,** run the full check, and show kibi's signoff summary when requirements changed.

## Evidence, as kibi counts it

kibi counts a requirement as *tested* only when an end-to-end test of one of its scenarios has a fresh, passing receipt from `kibi prove`, bound to the code it ran against and at most seven days old. That is the bar, and no shortcut lowers it:

- Every test entity declares its `verification_scope` (`unit`, `integration` or `end_to_end`), matching what the test really runs. A unit or integration test is never relabelled to count as end to end.
- Unit and integration tests prove the pieces and stay linked to the symbols they cover (`covered_by`); their receipts are recorded but don't make a requirement tested.
- End-to-end tests in `test/e2e` carry a `kibi.proof-contract.v1` for the end-to-end integration, which `kibi proof inspect` proposes and `.kb/proof/integrations.json` holds; nobody hand-writes either. CI's end-to-end job runs `kibi prove`, and the requirements report the site publishes from `main` shows that run's receipts.
- An agent may add scenarios and tests that verify a firm requirement, and link them to it, without the author; it never changes a firm requirement's statement.
- A behavior the owner relies on gets an end-to-end scenario. Each milestone's acceptance criteria (D-200 for M0) become scenarios verified end to end, so *tested* grows where it matters, not by count.

## Setup notes

- kibi and its Go symbol plugin are pinned npm dev dependencies, installed by `task setup`. `npm ci` then applies [patches/kibi-cli+2.36.0.patch](../../patches/kibi-cli+2.36.0.patch) and [patches/kibi-core+0.26.1.patch](../../patches/kibi-core+0.26.1.patch) with patch-package, and fails if either doesn't apply to the installed version, so a kibi upgrade has to carry both patches forward or drop them.
- `.kb/proof/integrations.json` holds three command integrations, all written by applying `kibi proof inspect` plans: `unit` (`go test ./...`, kibi's default proposal, which no test names yet), `e2e` (`task e2e`) and `e2e-ghostfolio` (`task e2e:ghostfolio`, the Ghostfolio shard). `task e2e:prove` runs `kibi prove --integration e2e` and `task e2e:prove:ghostfolio` runs `kibi prove --integration e2e-ghostfolio`; CI's e2e and e2e-ghostfolio jobs run them on k3d and kind, and the docs build ingests all four runs' artifacts before rendering the report ([pipeline.md](pipeline.md#ci-on-pull-requests-and-main)). Which of M0's exit criteria (D-200) the suite verifies, and which it doesn't yet, is in [pipeline.md](pipeline.md#not-built-yet).
- `.mcp.json` registers kibi's MCP server for Claude Code; other agents start the same server.
- kibi's own git hooks stay uninstalled: lefthook runs the same checks through task targets.
- kibi's sync sometimes publishes a broken compiled store, about one run in ten under load: a relationship missing or an entity twice, although the same files compile correctly next time. Until kibi fixes it upstream, the repository carries a local patch that lets the compiling process finish before the store is published, `task kibi:check` recompiles once on exactly that defect and treats the second check as final, and the bug is reported to kibi's maintainers, with the author reviewing the report before it is filed. Any other failure is final at once.
  - The same defect also publishes stores with records stored twice. At 08788ac every `kibi sync --rebuild` published exact duplicate triples, 9,000 to 10,000 of the 17,468 entities twice; duplicate answers multiply in kibi's requirement proofs, so the docs build's coverage query ran past kibi's 120-second query limit. A second local patch, to kibi-core, removes duplicate triples when the engine attaches a store; with it that commit's coverage query took 37 to 44 seconds and answered correctly. The removal is loud: the next kibi command prints `kibi (local patch): removed N duplicate triples (M entities stored twice) from the published store` on stderr, as a workflow warning under GitHub Actions. It is journaled, so the store on disk is repaired, and the line shows only on commands served by the engine that first attached the published store.
  - A query past the 120-second limit is stopped: kibi 2.36 already ends that query's Prolog process and gives the next request a fresh session (a forced timeout followed by another query answered in about 3.5 seconds), but its message said `killed=no`, read before the stop, and called the engine wedged. The kibi-cli patch makes the message report the stopped process. The limit itself stays, since a query that needs longer is a defect to find. A coverage query's cost has two parts: a fixed one of about 28 seconds per call (kibi's quadratic contradiction-witness step) and one per requirement row. Asking for the whole report in one query, on the reasoning that paging only multiplied the fixed cost, was wrong: with 1,231 rows that one query took 123 to 131 seconds as a command, about 95 of them in the query, close to the limit. So `task docs:gen` asks for it 300 requirements at a time through [kibi-coverage.sh](../../scripts/kibi-coverage.sh): with 1,239 requirements, five pages took 43, 42, 41, 36 and 31 seconds, about 3 minutes 15 seconds in all. Each page runs through [kibi-timed.sh](../../scripts/kibi-timed.sh), which prints how long the command took and warns from 90 seconds, three quarters of the limit, as a workflow warning in CI. A cheap query runs first, so attaching the store, and deduplicating one kibi sync just published (16 seconds on the D-97 follow-ups' knowledge base), stays out of the first page's limit. The command's own work adds about 30 seconds to the query, which is why the warning isn't at half the limit; once kibi fixes the quadratic contradiction-witness step upstream, the guard moves to timing the query alone, at half the limit. Outside CI the joined report is cached by a hash of the `.kb` files, kibi's versions and both patches, so a commit that doesn't change them doesn't pay those minutes again ([docs.md](docs.md#build-and-publishing)); CI always asks kibi afresh.
  - Both are part of the report for kibi's maintainers that the author reviews before it is filed.
