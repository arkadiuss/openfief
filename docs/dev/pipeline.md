This page explains the machinery that takes a change from a commit on a branch to signed container images, a tagged release and the demo environment. It describes what the repository contains today, file by file. The rules this machinery enforces are in [sdlc.md](sdlc.md) and aren't repeated here. Where the two disagree, [Not built yet](#not-built-yet) says so.

## Concepts

**One entry point.** Make, written by Stuart Feldman at Bell Labs in 1976, gave a project one file that names every build step. [Task](https://taskfile.dev) follows the same idea, with YAML instead of Makefile syntax. In OpenFief, [Taskfile.yml](../../Taskfile.yml) is the only place a command is written down. A developer, a git hook and a CI job all run `task <target>`, so they can't drift into three slightly different scripts. The Taskfile also pins the version of every tool it calls.

**Shift-left checks.** "Shift left" (Larry Smith, 2001) means running a check earlier, when a failure is still cheap. In git, the earliest point is the pre-commit hook: the commit doesn't exist until its checks pass. [lefthook](https://github.com/evilmartians/lefthook) manages the hooks. It writes small scripts into `.git/hooks` that read [lefthook.yml](../../lefthook.yml).

**Conventional Commits.** A commit subject has the form `type(scope)!: summary`, as in `feat(ledger): add lots`. The convention grew out of the Angular project's commit guidelines. The type tells a machine what kind of change a commit is, and `!` or a `BREAKING CHANGE:` footer marks a breaking one. Here, the type decides which section of the release notes a commit goes in.

**CalVer and SemVer.** Semantic Versioning (`MAJOR.MINOR.PATCH`) is a compatibility promise: only a new major version may break you. That matters to code that depends on an API. Calendar Versioning puts the date in the number, as Ubuntu's `24.04` does, which tells a user how recent a release is. The product uses CalVer (`2026.11.0`). The protobuf contracts and SDKs are meant to use SemVer.

**DCO.** The [Developer Certificate of Origin](../glossary.md#other-terms-and-abbreviations) came from the Linux kernel in 2004, after the SCO lawsuits made the origin of code a legal question. Each commit carries a `Signed-off-by: Name <email>` trailer (`git commit -s`), by which the author certifies they may contribute it. It's lighter than a contributor licence agreement: there's nothing to sign beyond the commit itself. D-5 in [DESIGN.md](../DESIGN.md) requires it.

**Keyless signing.** [cosign](../glossary.md#other-terms-and-abbreviations) is the signing tool of Sigstore, a Linux Foundation project launched in 2021. Classic signing needs a long-lived private key that someone must guard and rotate. Keyless signing replaces the key with an identity. The CI job asks GitHub for an OIDC token that names the repository, workflow and ref. Sigstore's certificate authority, Fulcio, exchanges it for a certificate that is valid for about ten minutes. cosign signs with a throwaway key and records the signature in Rekor, a public append-only log. A verifier checks who signed (the workflow identity) rather than which key.

```mermaid
sequenceDiagram
  participant J as "images.yml build job"
  participant O as "GitHub OIDC"
  participant F as Fulcio
  participant R as Rekor
  participant G as GHCR
  J->>G: push the image, receive its digest
  J->>O: ask for an ID token (id-token write)
  O-->>J: token naming repository, workflow and ref
  J->>F: token plus an ephemeral public key
  F-->>J: short-lived certificate for that identity
  J->>J: sign the digest with the ephemeral key
  J->>R: record signature and certificate
  J->>G: store the signature next to the image
```

**Digest pinning.** An image tag such as `:main` is a movable pointer. A digest (`@sha256:...`) is the hash of the content, so it changes if one byte changes. Pinning a digest means you run exactly what was tested and signed. Here, GitHub Actions are pinned by commit SHA, Dockerfile base images by digest, and cosign signs the digest the build produced. D-17 requires plugin images to be pinned by digest.

**GitOps.** In a push deploy, CI holds a credential for the cluster and runs `kubectl apply`. GitOps, a name Weaveworks gave the practice in 2017, turns this around: an agent inside the cluster pulls the desired state from a versioned source and keeps the cluster matching it. [Flux](https://fluxcd.io), a CNCF project that grew out of Weaveworks, is such an agent. Nothing outside the cluster needs a way in, and the source's history is the deploy log. The demo's Flux pulls from git and from a signed OCI artifact: a registry entry that holds manifests instead of an image.

**Supply-chain hygiene with Renovate.** Exact pins stop surprise upgrades, but they go stale. [Renovate](https://docs.renovatebot.com) is a bot that finds pinned versions and opens pull requests to bump them, so each upgrade is a reviewed and tested change. It can't see a pin it can't parse, so the Taskfile and workflows mark versions with `# renovate:` comments.

**Affected-only checks.** In a repository with many packages, most commits touch a few of them. Build systems such as Bazel and Pants (and `go test` itself, through its cache) avoid repeating work whose inputs didn't change: they know each target's inputs and rerun only the targets downstream of a change. OpenFief does the same with a small selector, [tools/affected](../../tools/affected/main.go). Go's import graph (`go list`) says which packages a changed package reaches; the selector reruns lint and tests for those, and nothing else. A change it can't place, or one that every check reads, such as `go.mod`, runs everything: a check skipped wrongly costs more than a check run needlessly.

**Traceability gate.** In safety-critical engineering, a traceability matrix links each requirement to the code that implements it and the test that verifies it. [kibi](kibi.md) keeps that record in `.kb/` and checks it with Prolog rules. Its gate in the pre-commit hook refuses a commit whose behavioral code has no owning requirement or no covering test.

## How it works

### The Taskfile

Every step is a task target, and `task --list` shows them with descriptions. Three conventions recur:

- **Pinned tools in `.bin/`.** The `vars` block pins golangci-lint, govulncheck, lefthook, Task itself, actionlint, controller-gen, Hugo, buf and its three generators (Go, Connect and the read API's OpenAPI), zed (SpiceDB's CLI, for the authorization schema), and for the demo hcloud, kustomize and gojq. The internal `tool:*` targets `go install` them into `.bin/`, and a `status` check skips the install unless the version changed. Go tools are built with the toolchain in `go.mod` (`GO_TOOLCHAIN`, now `go1.27.4`), because golangci-lint refuses code that targets a newer Go than it was built with. The envtest API server and etcd come from [envtest-assets.sh](../../scripts/envtest-assets.sh), which checks each archive against a pinned SHA-512. The flux CLI can't be built with `go install`, so `tool:flux` downloads its release archive and checks a pinned sha256. The k3s and Flux versions a demo machine installs are pinned here too, with their sha256 sums, and rendered into its cloud-init. `CNPG_VERSION` with `CNPG_MANIFEST_SHA256`, the sha256 of CloudNativePG's release manifest, pins the manifest every release bundle ships and the end-to-end suite installs: the internal `cnpg:manifest` target downloads it from CloudNativePG's GitHub release into `.bin/cnpg/` and checks the sum, and the install guide gives the same version and sum, which the release bundle's script test checks. The end-to-end suite also reads `K3S_VERSION` again, as the k3s image of the k3d cluster (`task e2e:k3s-image`). Every download of ours goes through [retry.sh](../../scripts/retry.sh), and CI caches `.bin/` by these versions ([Download retries and the tool cache](#download-retries-and-the-tool-cache)).
- **Explicit paths.** Tasks call `{{.BIN}}/golangci-lint`, not `golangci-lint`, so a global install can't shadow the pin.
- **Skip until it exists.** Some targets print "skipping" and succeed while their input is missing: `GO_GUARD` (no `go.mod`) and `PROTO_GUARD` (no `.proto` files). The pipeline was built ahead of the product. Today nothing skips: `go.mod` and the contracts in `proto/` exist, and `e2e` runs the suite in `test/e2e`.

Two targets drive a browser and are in no check, since a check must not need Chromium: `task design:icons` renders the built-in UI's app icons from the Seal with [app-icons.mjs](../../scripts/app-icons.mjs) ([Design system](design-system.md)), and `task ui:browser` runs [ui-browser.mjs](../../scripts/ui-browser.mjs), which serves the UI over its in-memory fakes and checks it at phone and desktop width, the Inbox and the check pages D-192 removed landing on it at 360 px, an account's tabs, an instrument's page with its rename and the overview's allocation tab at 360 px, its service worker, the overview it keeps offline (D-151), and a protected action confirmed with a passkey from Chromium's virtual authenticator (D-183), saving screenshots to `SHOTS` ([Built-in UI](../concepts/ui.md#verification)). `ui:browser` still runs in CI and gates every release ([testing.md](testing.md)): [ui-browser.yml](../../.github/workflows/ui-browser.yml) runs it with the runner image's Chrome, called by ci.yml's `ui-browser` job and by release.yml (see [CI on pull requests and main](#ci-on-pull-requests-and-main) and [Releases](#releases)). Both find Chromium the way docs-diagrams.mjs does, and `ui:browser` installs the npm packages first (`kibi:install`) for playwright-core.

`task setup` runs once per clone. It installs the tools, runs `npm ci` for kibi, whose `postinstall` has patch-package apply the repository's kibi patch ([The kibi gate](#the-kibi-gate)), installs the lefthook hooks, and registers kibi's merge driver for the `.kb` files named in [.gitattributes](../../.gitattributes). CI runs `task setup:ci` instead, which skips lefthook and the merge driver and compiles the branch's knowledge base.

`check` (CI) and `check:commit:full` run the same steps in the same order, with two differences: CI also runs the docs staleness gate over the pushed range (`docs:fresh`; the hook's version runs at `commit-msg`), and the kibi step at the end differs. The hook's `check:commit` runs only the steps of `check:commit:full` that the staged change can affect, and falls back to all of them when in doubt ([Affected checks](#affected-checks)). Task runs a `cmds` list in sequence and stops at the first failure. "Each module" below means `GO_MODULES`: the core (`.`) and the Go SDK (`sdk/go`).

| Step | What it runs | Fails when |
|---|---|---|
| `gen:check` | `task gen` (controller-gen writes deepcopy code, [CRDs](../glossary.md#other-terms-and-abbreviations) and the operator's Role), then [gen-check.sh](../../scripts/gen-check.sh) | a regenerated file differs from the git index or is untracked |
| `plugins:labels:check` | [plugin-labels.sh](../../scripts/plugin-labels.sh) `check`; `task plugins:labels` writes the labels | a first-party plugin's `io.openfief.plugin.manifest` Dockerfile label, or a demo `Plugin`'s `spec.manifest`, differs from its `plugins/<name>/manifest.json` (D-42) |
| `fmt:check` | `golangci-lint fmt --diff` in each module (gofumpt with extra rules, goimports) | a file would be reformatted |
| `lint` | `lint:config` (`golangci-lint config verify`), then `lint:go` (`golangci-lint run`) in each module, with the `e2e` and `spicedb` build tags so the end-to-end suite and the SpiceDB contract test are linted too | any finding; [.golangci.yml](../../.golangci.yml) enables every linter except a commented list |
| `lint:ci` | actionlint on the workflows, with its shellcheck and pyflakes integrations off | a workflow error |
| `proto` | `buf lint`, `buf format --diff`, [proto-breaking.sh](../../scripts/proto-breaking.sh) (with the base's own `buf.lock`), [proto-check.sh](../../scripts/proto-check.sh) | a lint or format issue, a breaking change against the base that no new exception excuses ([below](#breaking-contract-changes)), or a stale `sdk/go/gen` or `gen/openapi` (the read API's OpenAPI document, generated from its protobuf and `read_service.openapi-base.yaml`, with the error responses [tools/openapierrors](../../tools/openapierrors/main.go) adds as `read_service.openapi-errors.yaml` assigns them; `proto:gen` and the check both run it after `buf generate`) |
| `vuln` | [vulncheck.sh](../../scripts/vulncheck.sh): govulncheck in each module, then `npm audit --audit-level=high` | a finding, or an unreachable vulnerability database |
| `test` | `test:go` (`go test ./...` with the envtest binaries) in each module, then `test:script` for each of the twenty-four `scripts/tests/*.test.sh` | any failure |
| `docs:check` | [check-docs.sh](../../scripts/check-docs.sh) | an undefined or duplicate GR, D, P, T, OQ or R ID, or a changed ground-rule line |
| `docs:build` | [docgen](../../tools/docgen/main.go) writes the reference pages, then Hugo and [docs-diagrams.mjs](../../scripts/docs-diagrams.mjs) build the site ([docs.md](docs.md)) | a broken link, a diagram that doesn't render, or a docs page naming a kibi ID or task that doesn't exist |
| `docs:fresh` (CI only) | `git log` over the range from `DOCS_BASE`, piped into `docgen fresh` | covered code changed without a page covering it and without a `Docs-Unchanged:` trailer, or a Go package no page covers |
| `demo:validate` | [validate.sh](../../scripts/demo/validate.sh): `kustomize build` of `deploy/demo`, of every git path its Flux Kustomizations apply, and of `deploy/demo/openfief` | a layer doesn't build, an image isn't pinned by digest, an OCI source doesn't require a cosign signature, or a substituting layer uses a variable cloud-init doesn't define |
| `authz:validate` | `zed validate authz/validation.yaml`, offline: the authorization model's SpiceDB schema ([authz/schema.zed](../../authz/schema.zed), D-164) against its relationships and assertions | the schema doesn't parse, or an assertion fails |

`task test:authz` is outside `task check`: it runs the authorization contract test ([test-authz.sh](../../scripts/test-authz.sh), build tag `spicedb`) against a real SpiceDB in testing mode, which must answer every holder and action as `identity.MayAct` does. SpiceDB is pinned as `SPICEDB_VERSION` and built from its module into `.bin/` on first use (`tool:spicedb`, through retry.sh), which takes minutes, so `task tools` doesn't install it.
| `kibi:check` or `kibi:staged` | `kibi check` through kibi-check.sh (CI); `kibi check-generated --staged --changed-only` and `kibi check --staged` through kibi-staged.sh (hook) | a knowledge-base rule violation |

Two steps compare against a base revision: the ground-rule check reads `DOCS_BASE`, and `proto:breaking` reads `PROTO_BASE`, then `DOCS_BASE`. Both default to `HEAD`, which locally means "against the last commit". CI sets `DOCS_BASE` to the pull request's base.

Until the first beta, a contract change marked breaking (`!` or a `BREAKING CHANGE:` footer) may break the contracts ([sdlc.md](sdlc.md#releases)). From the first beta, a breaking contract change goes in only when an author decision names it, as D-157 removes the read API's `ListBrokerAccounts`. `proto:breaking` excuses exactly what that decision names, in the change that makes it, and still fails on every other breaking change; once the change is on the base, later comparisons no longer see it. The commit marks it breaking (`!` or a `BREAKING CHANGE:` footer), so the release notes list it.

### Breaking contract changes

Which rule applies comes from the repository's tags (`tools/protobreak stage`, [stage.go](../../tools/protobreak/stage.go)): until a tag names a beta (`YYYY.M.N-beta.K`) or a stable release (`YYYY.M.N`), the check is before the first beta, and alpha tags don't change that. CI checks out the whole history with its tags, so it sees the same tags a clone does.

**Before the first beta**, any breaking change goes in, in a commit marked breaking (`!` or a `BREAKING CHANGE:` footer), so the release notes list it; it needs no exception. The check isn't off for that: `judge` reports each finding no entry excuses as allowed, then [proto-breaking.sh](../../scripts/proto-breaking.sh) compares each non-merge commit in the range that touches the contracts with its parent, and fails on one that breaks them without the mark. Locally the commit isn't written yet, so the `commit-msg` hook's `task proto:breaking:commit` does it for the staged contracts and the message being written. Exceptions entries are checked as below all the same.

**From the first beta**, only what an author decision names breaks:

[proto-breaking-exceptions.txt](../../scripts/proto-breaking-exceptions.txt) lists the removals author decisions approved, one a line: the decision, the buf rule it excuses and the removed element, fully qualified, as in `D-157 RPC_NO_DELETE openfief.views.v1.ReadService.ListBrokerAccounts`. [proto-breaking.sh](../../scripts/proto-breaking.sh) runs `buf breaking --error-format json` against the base. When buf finds nothing and the file is as on the base, it passes as before, without building anything else. Otherwise it builds the base's contracts into a buf image and hands buf's findings, the file now and at the base, and [DESIGN.md](../DESIGN.md) to `tools/protobreak judge` ([judge.go](../../tools/protobreak/judge.go)), which passes only when all of these hold:

- Every entry cites a decision that exists, and a method's entry cites one that names the method as code, such as `` `ListBrokerAccounts` ``.
- An entry excuses anything only while it is new, absent from the base's file. An entry already on the base never excuses a later removal, and the check is never off.
- Only removals of a method (`RPC_NO_DELETE`) or a top-level message (`MESSAGE_NO_DELETE`) can be excused. A new message entry must name a message the base has that a method removed under the same decision holds: its request, its response, or a message they hold. So D-157 excuses `ListBrokerAccounts`, `ListBrokerAccountsRequest`, `ListBrokerAccountsResponse` and `BrokerAccount`, and nothing else.
- Every finding is excused by a new entry, and every new entry excuses a finding. A field whose type changed next to the removal still fails, and so does an entry added before its removal or without one, so the file can't grow silently.

Commits are checked too, before and after the first beta. In the range from the base, every commit that adds an entry must be marked breaking (`tools/protobreak marked`). Locally, where the base is `HEAD` and the commit isn't written yet, the `commit-msg` hook runs `task proto:breaking:commit`, which does the same for the staged file and the message being written; it skips merge commits, whose commits the range check sees one by one. Removing an entry needs no mark. The entries stay in the file as the record of what was approved; once on the base, they excuse nothing.

### Affected checks

`task check:commit` runs [check-commit.sh](../../scripts/check-commit.sh). It writes the staged changes (`git diff --cached --name-status`) and both modules' package listings ([go-packages.sh](../../scripts/go-packages.sh): `go list -json`, once with the `e2e` tag and once without) to a temporary directory, and runs `tools/affected hook` on them. The tool prints the plan and the reason for every step it runs or skips, and lists the task targets on standard output; the script runs them in order, prints each one's time (`check-commit: <task>: 41s`) and the total, also after a failure, and stops at the first failure. If the tool fails, the commit fails. A merge needs no special case: while it is being committed the staged diff is the merge's diff against its first parent (`HEAD`), so the selection covers what the merge brings in, and merging a branch that only changes tests runs those tests and their lint, not the full check; `kibi check --staged` already leaves out files the merge takes unchanged from the other branch. `task check:plan` prints the plan without running it, and `FULL=1` (`FULL=1 git commit ...`, or `task check:commit FULL=1`) runs `check:commit:full`. The tool itself never runs git, go or task: the scripts collect their output, as docgen's Taskfile targets do.

The tool sorts each changed path by the first rule that matches it, in [classify.go](../../tools/affected/classify.go):

| Change | What the hook runs |
|---|---|
| `go.mod`, `go.sum`, `go.work`, `go.work.sum` (both modules), `.golangci.yml`, `Taskfile.yml`, `lefthook.yml`, `tools/`, `scripts/`, `proto/`, `buf.*`, generated code (`gen/`, `sdk/go/gen/`), `design/`, `authz/`, `package.json`, `package-lock.json`; a file in no rule, package or test's reach; a Go file in a directory that is no package (a package removed or not yet listed); a path with whitespace | everything: `check:commit:full` |
| A Go file | its package is changed. Lint and `govulncheck` run on it and on every package that imports it, directly or not (reverse imports from `go list`); tests run on those and on every package whose tests import one of them. A package with no files without a build tag, such as `test/e2e`, is only linted: govulncheck and `go test` build without tags. `fmt:check:files` checks the staged Go files. |
| A file a package embeds (`go:embed`, from `go list`'s `EmbedFiles`) | the same as a Go file of that package |
| Any other file under a package's directory (test data, a Dockerfile) | that package's tests |
| A path a package's Go files name as a relative literal (`"../../deploy/crds"`, `filepath.Join("..", "deploy")`) | that package's tests |
| A path a script test names as `$root/<path>`, `$root/.github/workflows` included | that script test (`test:script`) |
| `docs/`, `site/`, root `*.md` and `LICENSE` | `docs:build` |
| `.kb/` | `docs:build` (its status pages read kibi) |
| `.github/` | `lint:ci` |
| `deploy/` | `demo:validate`; `gen:check` for `deploy/crds` and `deploy/operator` |
| A plugin's `manifest.json` or `Dockerfile`, or `deploy/demo/` | `plugins:labels:check` |
| `.claude/`, `.mcp.json`, `renovate.json` | nothing more: no check reads them |
| Operator code, through its imports | `gen:check` |
| A deleted file | `docs:build`, since a page may link to it |

`docs:check` (a second) and `kibi:staged` always run, and the commit-msg hook's `docs:fresh:commit` is unchanged. So a commit of docs or requirements alone runs `docs:check`, `docs:build`, `kibi:staged` and the staleness gate, and no Go step. Collecting the inputs and compiling the tool take a few seconds. Measured with `task check:commit` on this repository's 66 packages, a warm Go cache and other work on the machine:

| Staged change | Steps | Time (kibi 2.42) | Time (kibi 2.36) |
|---|---|---|---|
| One plugin's `main.go` | fmt, lint, govulncheck and tests of that plugin; plugin-labels.test.sh; kibi:staged | 22 seconds (kibi 13) | about the same |
| `internal/ledger` (about 50 packages import it) | fmt, lint, govulncheck and tests of 50 packages, kibi:staged | 37 seconds | about 1 minute |
| A page under `docs/`, or a record under `.kb/` | docs:check, docs:build, kibi:staged | 90 to 100 seconds, almost all in docs:build | 3 minutes or more; 20 to 25 minutes with `.kb/` staged |
| `Taskfile.yml` or `go.mod`: check:commit:full | everything | 170 seconds (the kibi upgrade commit) | 35 to 38 minutes |

The architecture tests ([tools/archtest](../../tools/archtest/doc.go), [code-organization.md](code-organization.md#architecture-tests)) read the whole repository, and name the directories they walk as relative literals (`"../../internal"`, `"../../plugins"` and the others), so the hook reruns them for a change under any of those directories. A new bounded context is added to the tests' context map (`tools/archtest/layout.go`) with the table in code-organization.md; a test that skips without PostgreSQL is listed in `exceptions.txt` with its reason.

The hook is less strict than CI by design: CI's `task check` stays whole, and runs on every pull request and every push to `main`. Linting a subset of packages can miss a finding that needs other packages (`dupl` compares code across packages), and a test that reads a file through a path built at run time, rather than a literal, isn't rerun when that file changes. [testing.md](testing.md#stability) asks tests to name such files with literal paths.

### Download retries and the tool cache

Every download CI makes of its own goes through [retry.sh](../../scripts/retry.sh): the envtest archives ([envtest-assets.sh](../../scripts/envtest-assets.sh)), the flux CLI (`tool:flux`), CloudNativePG's manifest (`cnpg:manifest`), the Envoy Gateway and Gateway API manifests ([e2e-gateway.sh](../../scripts/e2e-gateway.sh)), the `go install` of every pinned tool and of Task itself, `npm ci` (`kibi:install`) and `gh release download` in the release smoke test. The script runs the command again when its error text says a later try can work: HTTP 429 or 5xx, a curl connection, DNS or timeout error, a Go or npm network error. It never retries anything else: a 4xx answer other than 429, a certificate problem, a failed checksum or a compile error is final at once. The first failure is followed by up to five more tries, after 2, 4, 8, 16 and 32 seconds, and each wait and its reason are printed. The checksum checks stay in the callers, after the download, exactly as strict as before. `tool:envtest` once failed with curl's exit 22 on a 504; curl's own `--retry 3` waited a few seconds in all.

Keyless signing goes through it too: `image:sign`, `deploy:demo`'s signature of the demo's manifests and `release:cli:sign`. It retries only the failures above and one of cosign's own, GitHub's token service answering an error page where cosign expects its OIDC token as JSON; a refusal by Fulcio or Rekor stays final (`image:sign` keeps its one extra run for Rekor's 409). The cosign installer is a third-party action, which a script can't wrap. The local composite action [install-cosign](../../.github/actions/install-cosign/action.yml) runs `sigstore/cosign-installer` (pinned as before), again after 15 seconds and a last time after 45 if it fails, the first two failures being only warnings; it retries any installer failure, since the action can't say why it failed. All eight workflow steps that installed cosign call it. The other third-party actions that fetch things (setup-go, setup-node, the cluster actions) aren't wrapped.

The setup action caches `.bin/` (without `.bin/e2e`, the e2e job's own state) with `actions/cache`, keyed by runner, job and a hash of the Taskfile's `*_VERSION` and checksum variables plus `go.mod`'s `go` and `toolchain` lines. The tool targets skip an install whose binary is already at the pinned version, so a hit makes `task setup:ci` nearly free, and a bumped version builds a new cache.

### Git hooks

[lefthook.yml](../../lefthook.yml) defines five hooks. Each calls task targets with `.bin/` first on `PATH`, so the pinned Task runs:

- `pre-commit` runs `task check:commit`, which runs only the checks the staged change affects ([Affected checks](#affected-checks)).
- `commit-msg` runs `task docs:fresh:commit` with the message file: the docs staleness gate on the staged files. It skips merge commits; CI checks the merged commits one by one. It also runs `task proto:breaking:commit`, which fails a commit that adds a breaking-change exception, or before the first beta breaks a contract, without marking itself breaking ([Breaking contract changes](#breaking-contract-changes)), and skips merges the same way.
- `post-checkout` runs `task kibi:sync` for a branch checkout (lefthook's `{3}` argument is `1`), not for a file checkout.
- `post-merge` runs `task kibi:sync`.
- `post-rewrite` runs `task kibi:sync` after a rebase, not after an amend.

kibi compiles one store per branch, and the sync hooks keep it in step with the branch you're on. kibi's own git hooks stay uninstalled, so lefthook alone owns `.git/hooks`.

The hook checks the working tree, not a clean copy of the index. Go tests, lint and the docs check read files on disk, so an unstaged edit can make a commit pass locally and fail in CI. Only `gen:check` and the kibi gate compare against the index.

### The kibi gate

On commit, `kibi:staged` runs two commands. `kibi check-generated --staged --changed-only` regenerates kibi's symbol manifest from the staged bytes and compares it with what is staged; it skips the work when no staged path can affect a symbol. `kibi check --staged` then runs kibi's rules on the staged change, including the rule that blocks a behavioral symbol with no `implements` requirement or no `covered_by` test. kibi's own help marks `--staged` as experimental.

[kibi-staged.sh](../../scripts/kibi-staged.sh) runs both. First it removes the throwaway stores (`/tmp/kibi-precommit-<pid>-*`, tens of megabytes each) that earlier `kibi check --staged` runs left behind when they were killed, only those whose process is gone. `kibi check --staged` builds one such knowledge base per run, in a Prolog process of its own, to apply the staged symbols to the branch's records; a local kibi patch keeps that store off the disk ([Setup notes in kibi.md](kibi.md#setup-notes)), which is what keeps the step at about 30 seconds for a one-file commit.

In CI, the setup action sets `KIBI_BRANCH`, because `actions/checkout` leaves a detached HEAD and kibi won't write a store without a branch name. `setup:ci` then runs `kibi sync`, and `task check` ends with `kibi check` over the whole knowledge base. CI is therefore stricter than the hook: it also catches problems outside the staged change.

kibi's `kibi sync` ends its compiling Prolog process with a SIGTERM right after detaching the store, and publishes the store straight after, the suspected cause of stores published without some of their records under load ([Not built yet](#not-built-yet)). [patches/kibi-cli+2.42.0.patch](../../patches/kibi-cli+2.42.0.patch), applied by patch-package on every `npm ci` (package.json's `postinstall`, with `--error-on-fail --error-on-warn`, so a patch that no longer applies, or a kibi-cli at another version, fails the install), makes the sync wait up to 60 seconds for that process to halt on its own after `kb_detach`, and refuses to publish when the detach failed or the process had to be signalled. `task kibi:check` also runs `kibi check` through [kibi-check.sh](../../scripts/kibi-check.sh), as a stopgap kept until kibi fixes the defect upstream: the patch makes the defect rarer, not gone. When the check fails naming a compile defect, an authored relationship "missing from the compiled KB" or a duplicate row in the paginated entity projection, the script compiles the store again from the same files with `kibi sync --rebuild` and checks once more; that check's result is final. Any other failure is final at once, and a real authored problem, such as an endpoint declared in a file Git doesn't track, survives the recompile and still fails. The same applies after a merge: run `kibi sync --rebuild`, then `task kibi:check`.

The same defect publishes stores with records stored twice, which multiplies the answers of kibi's requirement proofs until a query passes kibi's 120-second limit. [patches/kibi-core+0.31.0.patch](../../patches/kibi-core+0.31.0.patch) removes exact duplicate triples when the engine attaches a store, and the kibi-cli patch prints how many it removed on the next kibi command's stderr; under GitHub Actions the line is a `::warning::` workflow command, so it shows on the run's summary page whichever job's command meets it first. The same patch reports a query stopped at the limit as stopped, which kibi's own message didn't. `task docs:gen` asks for the coverage report 300 requirements at a time through [kibi-coverage.sh](../../scripts/kibi-coverage.sh), and runs each page through [kibi-timed.sh](../../scripts/kibi-timed.sh), which prints how long it took and, from 90 seconds, three quarters of the limit, warns, again as a workflow warning in CI; a cheap query before the first page takes the store's attach and dedupe out of its limit. Outside CI the joined report is reused while the `.kb` files, kibi's versions and its patches are unchanged, so the pre-commit hook doesn't pay about four minutes on every docs commit; in CI, where `CI` and `GITHUB_ACTIONS` are `true`, it is always regenerated ([docs.md](docs.md#build-and-publishing)). [kibi.md](kibi.md#setup-notes) has the measurements.

### CI on pull requests and main

[ci.yml](../../.github/workflows/ci.yml) runs on pull requests to `main`, on pushes to `main`, and by hand (`workflow_dispatch`), which runs like a push. The workflow starts from `permissions: {}`, and each job asks only for what it needs. A newer push supersedes a running pull-request run, but runs on `main` always finish, one at a time, so every merge is built.

Each job first calls the composite [setup action](../../.github/actions/setup/action.yml). It installs Go from `go.mod`, installs Task at the Taskfile's `TASK_VERSION` and sets `KIBI_BRANCH`. Task is the one tool installed outside a task target, since no target can run before Task exists; its install goes through retry.sh like the tool targets'. The action also restores `.bin/` from a cache ([Download retries and the tool cache](#download-retries-and-the-tool-cache)). By default the action also installs Node and runs `task setup:ci`; jobs that only need Task pass `tools: 'false'`.

- `plan` runs `task ci:plan`: `tools/affected ci` reads `git diff --name-status <base> HEAD` and prints `code=false` for a pull request whose every path is docs, requirements or agent configuration (`docs/`, `site/`, `.kb/`, root `*.md`, `LICENSE`, `.claude/`, `.mcp.json`, `renovate.json`), and `code=true` otherwise and on every push. `test-pg`, `e2e` and `e2e-ghostfolio` run only with `code=true`. It also prints `ui=true` on every push, and for a pull request that changes anything `ui:browser` reads: `internal/views` (the UI, its templates and static files, and the views it renders), `plugins/ui`, `design/`, `scripts/ui-browser.mjs`, the workflows and setup action that run it, the npm packages and their patches, `Taskfile.yml`, `go.mod` and `go.sum`; `ui-browser` runs only with `ui=true`. So a push to `main` always runs the whole suite.
- `check` runs `task check` with full history, whatever changed. `DOCS_BASE` is the pull request's base SHA, or the previous `main` (`github.event.before`) on a push.
- `test-pg` runs `task test:pg`. [test-pg.sh](../../scripts/test-pg.sh) starts a throwaway PostgreSQL from the runner's binaries on a Unix socket, each test creates a fresh database with every migration applied, and the server is removed afterwards. The same run loads the demo dataset end to end through `cmd/demo-seed`, and starts `cmd/core` on a fresh database to call its read API with a script token.
- `ui-browser` calls [ui-browser.yml](../../.github/workflows/ui-browser.yml), which runs `task ui:browser` with Node and the runner image's Chrome, as the e2e passkey test finds it, so a page that scrolls sideways at 360 or 390 px in either theme, a phone menu that doesn't fold, a UI that isn't installable or a service worker that caches a page fails the run. It uploads the screenshots, pass or fail, as `ui-browser-screenshots`, kept seven days.
- `dco` runs on pull requests and on pushes to `main`: `task dco BASE=<base sha> HEAD=<head sha>`, from the pull request's base or the push's previous head (its last commit alone when the push creates the branch). [dco-check.sh](../../scripts/dco-check.sh) walks each non-merge commit in the range and requires a `Signed-off-by` trailer that matches the commit's author name and email exactly. The `commit-msg` hook runs the same check on the commit being made (`task dco:message`, `dco-check.sh --message`: the author from `git var GIT_AUTHOR_IDENT`, a merge exempt), so a commit without its author's sign-off is refused before it exists and a push that skipped the hook still shows red.

```mermaid
  docsbuild --> docsjob["docs: publish site/public to GitHub Pages"]
  testpg["test-pg: task test:pg"]
  uibrowser["ui-browser: ui-browser.yml, task ui:browser; uploads ui-browser-screenshots"]

  images -->|"push to main"| pub["build, push and task image:sign the affected images; task image:carry the others"]

```

**Images.** The `discover` job runs `task ci:images`. It lists each `cmd/<name>/Dockerfile` and `plugins/<name>/Dockerfile` as a JSON matrix and lowercases the registry prefix; today that is `core`, `demo-seed`, `egress-proxy` and `operator`, and the plugins `eodhd`, `ghostfolio`, `ibkr-flex`, `nbp-fx`, `treasury-bonds` and `ui`. An empty list skips `build` rather than failing it.

With `select` (CI, never a release), `discover` runs `task ci:images:select` instead ([ci-images-select.sh](../../scripts/ci-images-select.sh)), which hands `tools/affected images` the matrix, the package listings and, per image, an earlier build to compare with. An image is affected by its Dockerfile, by a non-test Go file of any package its binary imports, directly or not (from `go list`, so not from paths alone), by a file one of those packages embeds, and by the inputs every image shares: both modules' `go.mod` and `go.sum`, `go.work`, `go.work.sum`, `.dockerignore`, images.yml, the setup action, ci-images.sh and `tools/affected`. A Go file in no package rebuilds every image.

- On a pull request (`base`), the earlier build is the pull request's base: the affected images are built, not pushed, and the rest are skipped.
- On `main` (`reuse`), the earlier build is the newest of HEAD's last 20 first-parent commits whose `sha-<commit>` tag carries a signature that `cosign verify` accepts from images.yml on `main`, the identity [pin-images.sh](../../scripts/demo/pin-images.sh) trusts. Comparing with that commit, not with the push's `before`, means a cancelled run or a failed build can't hide a change: the next run diffs against the last image that was really signed. An image with no such build is built.
- An unaffected image on `main` is carried: the `carry` job runs `task image:carry` ([image-carry.sh](../../scripts/image-carry.sh)) per image. It verifies the earlier digest's signature, tags that digest `sha-<commit>` and `main` with `crane tag` (pinned as `CRANE_VERSION`), which adds a tag without touching the manifest, and verifies that the new `sha-<commit>` tag resolves to the same signed digest. Nothing new is signed: the signature from images.yml on `main` belongs to the digest. So after every push, every image has a `sha-<commit>` tag on a digest images.yml signed, and the demo deploy finds one for each image as before. A carry that fails fails the run, and the deploy with it.

In a release (a `version` given), `build` fails fast: the first image that fails cancels the builds still running, so they don't push under a version that won't be released. CI runs let every image finish, so one failure doesn't hide another. `discover` prints its decision and the reason for each image in the job log, such as `carry nbp-fx: no input changed since 1a2b3c4` or `build core: internal/ledger/ledger.go is in internal/ledger, which it imports since 1a2b3c4`. `build` runs once per image. Buildx builds `linux/amd64` and `linux/arm64` from the repository root, attaches an SBOM and a full (`mode=max`) provenance attestation, and caches layers per image. The Dockerfiles copy `go.work`, `go.work.sum` and `sdk/go` and build in workspace mode, as the repository does locally, because the core imports the SDK module, which a private repository can't serve as a module version. They cross-compile Go on the build machine and copy the binary into a distroless base pinned by digest. When pushing, the job logs in to GHCR with the job's token, pushes, and runs `task image:sign IMAGE=<image>@<digest>`, so cosign signs the digest just pushed, never a tag. cosign v3 stores the signature as a Sigstore bundle attached to the digest as an OCI referrer. The operator verifies plugin images in that format and trusts `images.yml` on `main` as OpenFief's own signer, so signing has to stay in that workflow. The tags depend on the caller:

| Caller | Built | Pushed and signed | Tags |
|---|---|---|---|
| Pull request | the affected images | no | none |
| Push to `main` | the affected images; the others are carried | yes; a carried image keeps its signed digest | `sha-<short sha>` and `main`, on a new or a carried digest |
| Manual run with `all_images` | every image | on `main` | `sha-<short sha>` and `main` |
| Release | every image | yes, unless `dry_run` | the version, such as `2026.11.0-beta.1` |

### The demo

The demo is one Hetzner Cloud server running k3s, holding synthetic data only (GR-12). [demo.md](demo.md) is the operator's guide; it's a proposal, and this section only explains the machinery. The pipeline touches the demo in two ways.

**The machine.** `demo:plan`, `demo:up`, `demo:status`, `demo:down` and `demo:recreate` all run [demo.sh](../../scripts/demo/demo.sh) with the pinned hcloud CLI. They run from a terminal, or from [demo-infra.yml](../../.github/workflows/demo-infra.yml), a hand-started workflow in the GitHub Environment `demo`, which holds `HCLOUD_TOKEN` and `CLOUDFLARE_API_TOKEN`. The script keeps no state: it finds Hetzner resources by the labels `app=openfief` and `env=<name>`, and Cloudflare DNS records by the comment `managed-by=openfief-demo env=<name>`, so `up` creates only what is missing and `down` deletes only what is the demo's. With the Cloudflare token, `up` points `demo.openfief.dev` (an A and a CAA record) at the server, through curl and gojq; without it, `up` prints the record to create, and `DEMO_DOMAIN=none` falls back to an sslip.io name. `task dns:site` (`demo.sh dns-site`) keeps the website's records at `openfief.dev` and `www` the same way, under its own comment `managed-by=openfief-site`, and deletes the retired `docs.` record. When the project has no SSH key labelled `openfief-ssh=true`, `up` installs a throwaway public key whose private half is never stored, so Hetzner sets no root password. Before it creates anything, it prices the server and its IPv4 from Hetzner's price list in integer micro-euros. It refuses if the monthly total of all OpenFief resources would exceed `DEMO_BUDGET_EUR`, which defaults to 10 EUR. `down` and `recreate` need `CONFIRM` set to the demo's name. The server boots from [cloud-init.yaml](../../deploy/demo/cloud-init.yaml), filled in with the Taskfile's pins. It installs k3s and Flux, checking each download's sha256, and points Flux at `deploy/demo` on `main`.

**Deploys.** Nothing outside the machine holds a credential for the cluster. Flux follows two kinds of source, declared in [stack.yaml](../../deploy/demo/stack.yaml). The platform layers follow `main` in git: the CRDs, the CloudNativePG operator and database, cert-manager and the Let's Encrypt issuer. OpenFief itself, today the operator, the egress proxy, the core, the demo's plugin instances and the `demo-seed` Job that loads the synthetic demo dataset ([demo.md](demo.md#demo-data)), follows a signed OCI artifact, and so do the demo's routes to it, so a route never changes before the core it points at. [deploy-demo.yml](../../.github/workflows/deploy-demo.yml) publishes it by running `task deploy:demo TAG=<tag> REPO=<owner/repo>`, where the tag is `sha-<short commit>` for `main` or the version for a beta:

1. [pin-images.sh](../../scripts/demo/pin-images.sh) runs `cosign verify` on each image at that tag. It accepts only a signature from `images.yml` on `main`, and writes the verified digest over the all-zeros placeholder in `deploy/demo/openfief/kustomization.yaml`. It also names the Job that generates the platform's credentials (D-216) `openfief-init-credentials-<the first 12 hex digits of the core's digest>`, since a Job's pod template can't change: each new core image is a new Job, and Flux prunes the old one, with no force annotation. One unverified image fails the deploy. A carried image's `sha-<commit>` tag points at a digest an earlier run signed, so it verifies like a fresh one.
2. validate.sh checks the result, and kustomize renders it into the artifact's `app/`, and `deploy/demo/routes` into its `routes/`; [render-audit.sh](../../scripts/demo/render-audit.sh) renders the egress audit, `deploy/demo/audit`, into its `audit/`, with the egress proxy's digest that just verified and the deploy's tag on the Job, so every deploy re-creates it.
3. `flux push artifact` pushes the manifests to `ghcr.io/<owner>/<repo>/demo-manifests:<tag>`. cosign signs that digest keylessly, and `flux tag artifact` moves the `demo` tag to it.
4. Flux on the machine checks the `demo` tag every two minutes. It applies a new artifact only if the signature comes from `deploy-demo.yml` on `main`.
5. After the app layer, Flux's `demo-egress-audit` layer runs the audit Job and waits for it: `egress-proxy audit` reads the egress proxy's logs and the `PluginGrant`s, read-only, and fails when the proxy allowed a request to a host outside the asking instance's grant, or a log line holds more than who asked, where to and the decision (D-200 criterion 16, GR-12; [Egress](../concepts/egress.md#auditing-the-log)). The demo's `nbp` instance reaches NBP's real API, so this is where real traffic is audited. A failed audit fails that layer on the machine; the deploy job doesn't see it.

The deploy job runs in the `demo` environment with `packages: write` and `id-token: write` and no secret. A concurrency group makes deploys queue instead of overlapping.

```mermaid
  participant K as "k3s on the demo"

  G-->>D: digests signed by images.yml on main
```

### Releases

[release.yml](../../.github/workflows/release.yml) only starts by hand (`workflow_dispatch`) and takes three inputs: `channel` (`alpha`, `beta` or `stable`), `version`, and `dry_run`, which defaults to `true`. Only one release runs at a time. An alpha is published exactly like a beta: a GitHub pre-release, deployed to the demo.

1. `plan` refuses a real run unless the actor is the repository owner and the ref is `main`. It then runs three tasks on full history. `release:check` calls [release-version.sh](../../scripts/release-version.sh): stable must be `YYYY.M.N`, beta `YYYY.M.N-beta.K` and alpha `YYYY.M.N-alpha.K`, with no `v`, no leading zeros, a month from 1 to 12, `K` from 1 up, and no existing tag. Given a release commit (`COMMIT`, which only `release:publish` passes), a tag already at that commit passes too, so a publish can resume; a tag anywhere else is still refused. The author picks `N` and `K`: `K` counts the pre-releases of one `YYYY.M.N`, so the first alpha of November 2026 is `2026.11.0-alpha.1` and the next `2026.11.0-alpha.2`; the script checks the form and that the tag is new, not that `K` follows the last one. `release:notes` writes the notes to the run's summary page. `release:assets` builds the docs site into `dist/openfief-docs-<version>.tar.gz`; this copy is only a trial and is discarded.
2. `ui-browser` calls [ui-browser.yml](../../.github/workflows/ui-browser.yml), as CI does, on the run's ref, dry runs included: a release needs the UI's browser checks green ([testing.md](testing.md)). `plugin-images` needs it, and every later job needs `plugin-images` or a job after it, so nothing is built, signed or published until they pass.
3. `plugin-images` calls images.yml with `kind: plugins`: only `plugins/*/Dockerfile`, with the version as the tag, pushed and signed only on a real run. Each pushed image's digest becomes an artifact, `digest-<name>`.
4. `catalog` runs only on a real run (D-88). `task release:catalog` ([release-catalog.sh](../../scripts/release-catalog.sh)) checks each digest's keyless signature by `images.yml` on `main` with `cosign verify`, then adds one entry per first-party plugin to [plugins.json](../../internal/plugins/catalog/plugins.json): its name, the release version, `ghcr.io/<repo>/<name>@<digest>` and the publisher `openfief` with OpenFief's CI identity. It refuses a plugin without a digest and a name and version already listed. The job commits the file on a new branch, `release/<version>`, and pushes it; that commit is the release commit.
5. `images` calls images.yml with `kind: commands` and `ref` set to the release commit, so the operator and core embed the catalog that pins this release's plugins. On a dry run there is no release commit and it builds the dispatching commit.
6. `bundle` renders the release's bundle from the release commit with `task release:bundle` ([release-bundle.sh](../../scripts/release-bundle.sh)) into the run's `bundle` artifact: `openfief-crds-<version>.yaml`, the `openfief` namespace, its LimitRange and the CRDs from `deploy/crds`; `openfief-install-<version>.yaml`, the operator, the egress proxy, the core and SpiceDB from `deploy/operator`, `deploy/egress-proxy`, `deploy/core` and `deploy/spicedb`; and the database the install brings by default (D-14): `openfief-db-<version>.yaml`, the minimal CloudNativePG cluster in `deploy/database`, with SpiceDB's `Database` and managed role (D-164) and a header that says what the owner may edit, and `cnpg-<CNPG_VERSION>.yaml`, CloudNativePG's release manifest byte for byte, which `cnpg:manifest` downloads and the script refuses unless its sha256 is the Taskfile's `CNPG_MANIFEST_SHA256`. An image the base already names by tag and digest is a third party's (SpiceDB, D-164; Authzed publishes no signature for it, so the digest pin is all there is to check): the script leaves it as the base pins it, neither takes nor verifies a digest for it, and `release-smoke.sh` and `release-verify.sh` check it is pinned instead of signed; a third party's image by tag alone is refused like ours. Renovate updates that image and the Taskfile's `SPICEDB_VERSION` together, and `release-bundle.test.sh` fails if they differ. The Job that generates the platform's credentials (D-216) runs the core's own image, which the script pins and `release-verify.sh` checks like any image of ours, and the script names that Job `openfief-init-credentials-<version>` (the version lowercased, its dots as dashes, at most 63 characters in all) under the stable label `app.kubernetes.io/name=openfief-init-credentials`, since an upgrade can't change a Job's pod template, and refuses a bundle without exactly that Job; the same test fails unless the Role of that Job is the only Role or ClusterRole in the install that grants `create` on Secrets, and grants nothing else. The script also refuses a `deploy/database` that isn't exactly the Cluster `openfief/openfief-db`. The digests come from the signing step itself: on a real run the job downloads every `digest-<name>` artifact the two image jobs wrote after `task image:sign`, and for each image the install names, it pins `ghcr.io/<repo>/<name>@<digest>` with kustomize's `images:`, after `cosign verify` (through [verified-digest.sh](../../scripts/verified-digest.sh)) confirms that `images.yml` on `main` signed that very digest. Files for images the install doesn't run, the plugins and `demo-seed`, are ignored: plugins come through the catalog (D-88) and the CLI (D-46). It refuses an image the install names without a digest, a digest that isn't sha256, an image that doesn't verify, and a base in `deploy/` that names its image with a tag or digest, and checks that the rendered install runs no other image. The files depend only on `deploy/`, the digests and the CloudNativePG manifest, so the same inputs give the same bytes. A dry run pushes and signs nothing, so it pins every image at an all-zeros placeholder digest (`PLACEHOLDER=1`) and checks the rest. Then `task release:images:verify` ([release-verify.sh](../../scripts/release-verify.sh)) checks the install file's images exactly as the [install guide](../guides/install.md#3-verify-the-images) tells the owner to, with `cosign verify` against `images.yml` on `main`: on a real run each pinned digest, on a dry run each image's `main` tag, which `images.yml` signed in main's last build, so a dry run exercises the guide's verification against real signatures too. `task e2e` renders the same bundle from the suite's registry and installs it ([CI on pull requests and main](#ci-on-pull-requests-and-main)); `task release:bundle VERSION=<v> IMAGES="<repository>@sha256:<digest> ..."` renders it locally from any set of images.
7. `cli` builds the `openfief` CLI from the release commit with `task release:cli` ([release-cli.sh](../../scripts/release-cli.sh)): static binaries for Linux and macOS on amd64 and arm64, `openfief-<version>-<os>-<arch>`, each stamped with the version (`-X main.version`, refused unless it holds only a version's characters) and built with `-buildvcs`, so `openfief version` prints the version and the release commit, a CycloneDX SBOM from `cyclonedx-gomod` (pinned in the Taskfile) and `openfief-<version>-SHA256SUMS`. `task release:cli:sign` then signs every file keylessly with `cosign sign-blob`, writing a Sigstore bundle, `<file>.sigstore.json`, next to it; the certificate names `release.yml` at the ref the run started from, `refs/heads/main` for a real run. `task release:cli:verify` checks `SHA256SUMS` and each file's signature as the [install guide](../guides/install.md#2-verify-the-cli) does, at the run's ref. A dry run signs and verifies too when the repository owner started it, so the signing is exercised for real before anything is published; all that leaves the run is the signature's entry in Sigstore's public Rekor log. Anyone else's dry run builds the CLI unsigned, so that a CLI signed as `release.yml` on `main` was always built by a run the owner started. The files are the run's `cli` artifact.
8. `publish` runs only on a real run, on the release commit, after `bundle` and `cli`. `task release:publish` repeats the version check with `COMMIT=HEAD`, checks that the four bundle files are there, rebuilds the docs tarball and the notes, and runs [release-publish.sh](../../scripts/release-publish.sh), which creates the tag at that commit through the GitHub API. Every channel gets the same assets: the notes, the four bundle files, the docs tarball and the CLI files; a stable release is a GitHub release, anything else a pre-release. It then opens a pull request from `release/<version>` to `main`, so the catalog reaches `main` through review rather than a direct commit. That needs the repository setting **Allow GitHub Actions to create and approve pull requests** (Settings, Actions, General, Workflow permissions): without it `gh pr create` fails with "GitHub Actions is not permitted to create or approve pull requests", after the tag and the release are already published, as it did for `2026.11.0-alpha.1`.

   Publishing is resumable. When `publish` fails part-way, **Re-run failed jobs** runs `publish` and then `deploy-demo` again on the same release commit, since the earlier jobs' outputs are kept. Each step checks what an earlier attempt already did: a tag already at the release commit is kept, and one at any other commit fails the version check; an existing release is not created again, and only the assets it lacks, compared by name, are uploaded (an asset whose upload never finished counts as missing and is replaced); an open or merged pull request from `release/<version>` is not opened again, while a closed, unmerged one doesn't count. Re-running the whole workflow instead doesn't resume, and isn't meant to: it would rebuild the images with new digests that no longer match the existing tag, so `plan` refuses the existing tag and the catalog step refuses an existing `release/<version>` branch, and both say to re-run the failed jobs to resume.
9. `deploy-demo` runs after every real alpha and beta. It publishes the beta's verified digests as the demo artifact, as above, with the version as the tag.
10. `smoke` runs after every real publish, alongside `deploy-demo`: it calls [release-smoke.yml](../../.github/workflows/release-smoke.yml) with the version, which installs the release just published the way the [install guide](../guides/install.md) tells the owner to, from the GitHub release's own assets and nothing the run built, and then audits the egress proxy's log against the `PluginGrant`s with `egress-proxy audit` built from the checkout, as the demo does after a deploy; the smoke test runs no connector, so the audit sees no allowed request, only that every line keeps to host, decision and instance. It runs after `publish`, so a failure doesn't hold the release back; it marks the run failed, and **Re-run failed jobs** runs it again.

[release-smoke.yml](../../.github/workflows/release-smoke.yml) also starts by hand (`workflow_dispatch`) for any published release: `version`, and `cli_version` (default `true`), which is `false` for a release that predates `openfief version`, `2026.11.0-alpha.1`. It asks only for `contents: read`, since the assets and the images are public, and uses no secret beyond the run's `GITHUB_TOKEN`. One job checks out the workflow's ref, for the harness only, installs cosign, creates a kind cluster (pinned like ci.yml's, with a `# renovate:` comment) and runs `task release:smoke`, which refuses a cluster that isn't local, installs the npm packages for playwright-core and runs [release-smoke.sh](../../scripts/release-smoke.sh) in a new, empty directory under `.bin`. The script follows the guide's steps with the guide's own commands: it downloads the assets with `gh release download`; verifies the CLI, `SHA256SUMS` and the SBOM with `cosign verify-blob` as `release.yml` on `main`, checks the checksums, and checks that cosign refuses the CLI under `images.yml`'s identity; puts the CLI on `PATH` and checks that `openfief version` prints the version and the commit the tag points at (read with `gh api`); verifies every image the install file names, each by digest, with `cosign verify` as `images.yml` on `main`, and checks that cosign refuses one under `release.yml`'s identity; checks CloudNativePG's manifest against the Taskfile's `CNPG_MANIFEST_SHA256` and applies it; applies the CRDs, the database and the install, waiting for the database and every rollout as the guide does; runs `openfief plugin install ui --yes` and waits for the UI's Plugin to be `Ready`; then starts `openfief enroll`, reads the one-time link it prints, has the runner's Chrome create the first passkey and sign in again with [passkey.mjs](../../test/e2e/passkey.mjs), the end-to-end suite's ceremony, and stops the CLI with SIGTERM, which it handles as Ctrl-C, expecting a clean exit. When a step on the cluster fails it prints the pods, events, plugins, the Cluster and the deployments' logs, never a Secret. The one-time link stays out of the log. Run it against a published release by hand with

```sh
gh workflow run release-smoke.yml --ref main -f version=2026.11.0-alpha.1 -f cli_version=false
```

[release-notes.sh](../../scripts/release-notes.sh) finds the previous release with `git describe`, limited to tags that start with four digits. A stable release skips alpha and beta tags, so its notes cover the whole cycle; a pre-release, alpha or beta, starts after the newest release of any channel. Each non-merge commit goes into Breaking changes (`!` or a `BREAKING CHANGE:` footer), Features (`feat`), Fixes (`fix`), Performance (`perf`) or Other changes, which also takes anything not in Conventional Commit form. A release's known limits go in `.github/release-notes/<version>/known-limits.md`, committed to `main` before the release starts: when the release commit has that file, its Markdown, the section's body without a heading, becomes a Known limits section ahead of the changes. A version without the file gets no such section, and an empty file fails the notes.

### Pins and Renovate

[renovate.json](../../renovate.json) enables four managers: Go modules, npm, GitHub Actions, and a regex manager for `# renovate:` comments in Taskfile.yml and `.github/`. `rangeStrategy: pin` keeps versions exact, and `helpers:pinGitHubActionDigestsToSemver` pins each action to a commit SHA with the version as a comment. Updates are grouped into one PR each for Actions, kibi, Taskfile tools, CI toolchains and Go modules. Renovate commits as `build(deps): ...` with a `Signed-off-by` line, so its PRs pass the DCO check and land under Other changes in the release notes.

| What | Pinned in | Kept current by |
|---|---|---|
| Go toolchain | `toolchain go1.27.4` in both `go.mod` files and `go.work`; `golang:1.27.4` by digest in the Dockerfiles | Renovate for `go.mod`; nothing for the Dockerfiles |
| Go dev tools, including Hugo, hcloud, kustomize and gojq | Taskfile `vars` | Renovate, "Taskfile tools" |
| kibi, Mermaid, playwright-core, patch-package | exact versions in [package.json](../../package.json), plus `package-lock.json` | Renovate (npm); kibi as one group, and a kibi-cli bump fails `npm ci` until the patch in `patches/` is moved to it or dropped |
| flux CLI; k3s and Flux on the demo machine | Taskfile `vars`, each with sha256 sums | Renovate bumps the version; the sums by hand ([demo.md](demo.md#update-the-pinned-versions)) |

## Verification

The pipeline's decisions live in shell scripts, and each script that decides something non-trivial has a test in [scripts/tests](../../scripts/tests). Each test works in a throwaway directory or git repository from `mktemp`. The git tests also clear `GIT_DIR` and its siblings, which a hook exports, so they can't touch the real repository. Each test is a kibi test record that covers a tooling requirement. `task test` runs all twenty-two in CI; the hook runs those that read a changed path, and all of them when `scripts/` changes. The selector's own decisions are table tests in [tools/affected](../../tools/affected/plan_test.go): change sets mapped to hook steps, images built or carried, and CI jobs (TEST-tooling-affected-plan, TEST-tooling-affected-images, TEST-tooling-affected-inputs). So are the breaking-change exceptions' in [tools/protobreak](../../tools/protobreak/judge_test.go): an approved removal with its new entries passes; a removal without them, another breaking change beside it, an entry already on the base, an entry that excuses nothing, a message the removed method never held, and a decision that is missing or doesn't name the method each fail; and an added entry needs `!` or a `BREAKING CHANGE:` footer; before the first beta, which only a beta or stable tag ends, a finding no entry excuses is allowed while the entries are still checked (TEST-tooling-protobreak).

actionlint checks the workflows only statically. To exercise the release workflow without publishing, dispatch a dry run from `main` with `gh workflow run release.yml --ref main -f channel=alpha -f version=2026.11.0-alpha.1 -f dry_run=true` (`dry_run` defaults to `true`, but say it), read the notes on the run's summary page, and download the `bundle` and `cli` artifacts. docker buildx imagetools inspect ghcr.io/arkadiuss/openfief/operator:main --format '{{ json .SBOM }}'

pin-images.sh trusts the first identity and Flux the second. Both assume that Fulcio names the reusable workflow that ran the job, not the workflow that called it; this page hasn't been checked against a real certificate. Because of that, the first also pins the repository and ref of the run, as every script that verifies an image or the CLI does ([verified-digest.sh](../../scripts/verified-digest.sh), [release-verify.sh](../../scripts/release-verify.sh), [release-catalog.sh](../../scripts/release-catalog.sh)): any repository may call `images.yml`. Flux's `matchOIDCIdentity` matches only the issuer and subject, so the demo's second identity can't pin them. Two layers keep both safe (D-181). First, every reusable workflow that signs, `images.yml` and `deploy-demo.yml`, runs its signing job only when `github.repository` is `arkadiuss/openfief`; in a called workflow that is the caller's repository, so another repository calling them gets the job skipped and no certificate naming the workflow. [reusable-signing-guard.test.sh](../../scripts/tests/reusable-signing-guard.test.sh) fails if any workflow with a `workflow_call` trigger has a job with `id-token: write` whose `if` doesn't require it. Second, Flux pulls only from this repository's GHCR package, which other repositories can't push to. On the machine, `flux get sources oci` and `flux get kustomizations` show what Flux verified and applied ([demo.md](demo.md#reach-the-demo)).

Nothing tests [assert-local-cluster.sh](../../scripts/assert-local-cluster.sh), gen-check.sh, proto-check.sh, envtest-assets.sh, test-pg.sh or go-packages.sh, a demo machine's boot, or the tasks only CI runs: `image:sign`, `deploy:demo` as a whole and `release:publish` (release-publish.sh, which it ends with, is tested against a stand-in `gh`). `crane tag` and the carry job have only run against fakes here; that `crane tag` keeps the digest is what crane documents, and image-carry.sh checks it on every carry.

- **The guide's downloads and verifications are tested only after a release** (testing.md). The bundle run installs from the bundle's files and runs the CLI built from the checkout, as testing.md asks; downloading the assets and the CLI from a release, and the guide's `cosign` and `sha256sum` checks, stay outside the suite. - **The dry run is per run, not a gate** (sdlc.md:42). A run with `dry_run: false` validates in `plan` and runs the UI's browser checks (`ui-browser`), then pushes and signs images straight away. Nothing requires an earlier dry run of the same commit, or checks that the commit passed CI. A release's image builds fail fast, which cancels the builds still running when one fails, but an image already pushed stays, under a version that is never released, and the plugin images are pushed before the other images are built.
- **No SDK or contract releases** (sdlc.md:43). There's no `sdk/go/vX.Y.Z` tagging and no TypeScript SDK. `buf breaking` now has contracts to check (the connector contract and the read API) and runs on every change, not only before an SDK release.

- **kibi's compile isn't deterministic.** On an unchanged tree, `kibi sync --rebuild` followed by `kibi check` failed 3 times in 30 runs here, with three clones of the same commit compiling at once on four CPUs: each time one to three relationships present in `.kb/relationships/` were missing from the published store (for example `verified_by SCEN-ledger-seed-concurrent->TEST-ledger-app-seed`). Rechecking the same store, on the same engine or after `kibi engine stop`, failed the same way, so the store on disk is wrong, not the running engine; the next compile of the same files passed. Each clone has its own store and its own engine socket (keyed by workspace and branch under `/tmp/kibi-runtime`), so worktrees don't share state: load, not sharing, is what the failures had in common. The CI failure on eaf5189 (`Full KB paginated entity projection returned duplicate entity ID`) reads as the same defect from the other side: `kb_query_entities` sorts unique ids, so a duplicate row means the store held one entity twice. The suspected cause was that `kibi sync` ends its compiling Prolog process with a SIGTERM right after `kb_save` and `kb_detach` (`terminate()` with no grace period) and publishes the staging directory straight after. The repository's patch ([The kibi gate](#the-kibi-gate)) lets that process halt on its own first, and in the same stress run, three clones each looping `kibi sync --rebuild` and `kibi check` twelve times, failures fell from 9 of 36 checks without the patch to 2 of 36 with it, every one of them a relationship missing from the compiled store. The patch makes the defect rarer but doesn't remove it, so the termination isn't the only cause; the sync's own count of the staging store before saving matched the authored files even in failing runs, which puts the loss between saving the store and the next check reading it. kibi-check.sh therefore stays: it recompiles once on such a failure, so a defect fails the gate only when two compiles in a row hit it. The defect's other face, records stored twice, became the rule rather than the exception at 08788ac (every rebuild, 9,000 to 10,000 entities twice), and the kibi-core patch removes those duplicates at attach time ([The kibi gate](#the-kibi-gate)); three rebuilds here removed 193,000 to 229,000 duplicate triples each. The report for kibi's author, with both patches as partial fixes, waits for the author's review before it is filed.
