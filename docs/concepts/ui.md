The built-in UI is OpenFief's default [view](../glossary.md) (D-3): a small website for the [owner](../glossary.md) that shows the record. It is a [plugin](../glossary.md) like any other, in its own pod, with the `view` capability and no egress host. It renders HTML on the server and reads the record only through the public [read API](../glossary.md) (D-6), the same API the owner's scripts use. This page explains how the browser, the UI and the core talk, how the owner signs in, what each page shows, and what is still missing.

## Concepts

**Backend for frontend.** The browser's application is the UI, and the UI talks to the core. This split, called backend for frontend (Sam Newman, 2015), keeps every credential out of the browser's reach: the UI holds the plugin's own token, and the owner's session token sits in a cookie that no script can read. The browser never calls the core's services itself, so the core's API needs no browser-facing CORS rules.

**The core is the front door.** Browsers reach the UI only through the core (D-81): the core is the only entry point for browsers, and it reverse-proxies every path the UI serves to the UI's pod, presenting its own token for that instance as it does to any plugin (D-59). So whatever route the owner adds, or a port-forward, reaches the core alone (D-28), and the UI, like every plugin, admits the core and nothing else. A reverse proxy is a server that forwards a client's request to another server and passes the answer back, so the client sees one origin. The UI's manifest declares the path prefix it serves, its [browser path](../glossary.md) `/`, and its grant approves it; `/` means every path the core doesn't serve itself.

**Two tokens, two jobs.** The UI presents two different tokens to the core:

- To the core's `openfief.identity.v1.AuthService` ([auth.proto](../../proto/openfief/identity/v1/auth.proto)), `openfief.portfolio.v1.ModelPortfolioService` ([model.proto](../../proto/openfief/portfolio/v1/model.proto)), `openfief.portfolio.v1.SleeveService` ([sleeves.proto](../../proto/openfief/portfolio/v1/sleeves.proto)), `openfief.ingest.v1.BondLotService` ([bond_lots.proto](../../proto/openfief/ingest/v1/bond_lots.proto)), `openfief.ingest.v1.StatementService` ([statements.proto](../../proto/openfief/ingest/v1/statements.proto)), `openfief.ingest.v1.AccountService` ([accounts.proto](../../proto/openfief/ingest/v1/accounts.proto)), `openfief.ingest.v1.TickerService` ([tickers.proto](../../proto/openfief/ingest/v1/tickers.proto)), `openfief.ingest.v1.SyncService` ([syncs.proto](../../proto/openfief/ingest/v1/syncs.proto)) and `openfief.valuation.v1.PriceCheckService` ([price_checks.proto](../../proto/openfief/valuation/v1/price_checks.proto)), its own projected ServiceAccount token with audience `openfief-core` (D-27), in the `Authorization` header. That proves the caller is a view plugin. The owner's session token travels in the request message (for a statement upload, in the stream's first message), with the browser's origin.
- To the read API, the owner's session token as the bearer token, like a [script token](../glossary.md). The plugin's token never reaches the read API, and the session token never goes into an `Authorization` header to the AuthService.

Projected tokens rotate, so the UI reads its token from the file the operator mounts (`OPENFIEF_TOKEN_FILE`) on every call, through the Go SDK's `CoreHTTPClient` and `TokenFile`.

**Sessions and scopes.** The core issues a session after an authenticator proves who is at the browser: a passkey (WebAuthn, D-26) gives an `owner` session; the demo authenticator gives a `read` session, without credentials, only on a demo database with the core's `--demo-sessions` flag. A `read` session sees the record; only an `owner` session manages passkeys, script tokens, enrollment links and the model portfolio, adds bond lots and uploads statements. The UI hides the owner's actions from a `read` session, but the core enforces the scope either way.

**Passkeys and the relying party.** WebAuthn binds a passkey to a relying party ID, the host name it was made on (W3C Web Authentication, Level 1 in 2019; Level 3 added JSON helpers). So a passkey made on `localhost` doesn't work on `demo.openfief.dev`, and D-60 makes the owner create one per host: the first through a one-time link on `localhost` over `kubectl port-forward`, later ones through a link that a signed-in session issues. The UI passes the WebAuthn options and credentials through untouched, in the Level 3 JSON forms, so the browser parses and serializes them with `PublicKeyCredential.parseRequestOptionsFromJSON`, `parseCreationOptionsFromJSON` and `toJSON()` and the UI ships no WebAuthn library.

**Server-rendered pages with htmx.** Pages are Go `html/template` output. [htmx](../glossary.md) swaps parts of a page in place: the allocation's dimension switch, the overview's chart card, the Ask box's answers and the "More transactions" button. Every htmx link is also a plain link, so the pages work without JavaScript, except passkeys and charts.

## How it works

The code is in [`internal/views/ui`](../../internal/views/ui/doc.go); [`plugins/ui`](../../plugins/ui/main.go) only wires it to the plugin's environment: the core's address (`OPENFIEF_CORE_ADDRESS`), the listen port (`OPENFIEF_LISTEN_PORT`) and the token file. There is no way to run it without a projected token, and no fixed token the core would accept instead (D-84): the UI is developed against a local cluster such as kind or k3d.

### The front door

`cmd/core` puts its front door, `withFrontDoor`, before what its browser port serves, the `http` port a route points at (D-115). A path the core serves itself goes to the core (`plugins.CoreServesPath`: `/healthz`, `/readyz`, `/v1` and below it, and every path whose first segment starts with `openfief.`, its Connect services). On this port that is the read API alone: the services only plugins call, the `AuthService` and the owner services, are on the plugin port, `connect`, and answer 404 here. Every other path goes to [`browserproxy`](../../internal/views/browserproxy/proxy.go), which asks [`app.FrontDoor`](../../internal/views/app/browser.go) where it goes:

- **Routes.** [`kube.Browser`](../../internal/views/kube/browser.go) watches the `Plugin` resources and the plugins' Services. A plugin serves browsers when it is not being deleted, its `Ready` condition is `True`, `view` is among its effective capabilities and its status holds an effective browser path, the one its manifest declares and its grant approves. At most one instance holds a browser path (D-114): the `openfief` CLI and the operator refuse a second ([Plugins](plugins.md), [Operator](operator.md)), because the core passes the browser's cookies, the owner's session among them, to the view. `views.RouteBrowserPath` ([browser.go](../../internal/views/browser.go)) sends a path to that one view when its prefix covers the path, whole segments only; should the core ever read more than one, it serves none rather than pick one.
- **The call.** The proxy sends the request to the instance's Service ClusterIP and `connect` port with the core's TokenRequest token for that instance (`identity/kube.CoreTokens`, the same as for connectors) in `Authorization`, replacing whatever the browser sent there. It keeps the browser's `Host`, sets `X-Forwarded-Proto` to the scheme the browser used (`https` on TLS or when the owner's Ingress in front says so, otherwise `http`) and `X-Forwarded-Host` to the `Host`, and drops every other `X-Forwarded-*` and `Forwarded` header a client sent. Bodies, uploads included, stream through.
- **Answers.** A path no plugin serves is 404. While the core hasn't read its cluster yet, or more than one view holds a browser path, 503. A plugin without an address, a token or an answer, 502. Outside a cluster there is nothing to proxy, and the read API answers such paths with 404.

The UI checks every request with the SDK's `RequireCore` and `NewCoreVerifier` (`requireCore` in [plugins/ui](../../plugins/ui/main.go)): a request without the core's token for the instance `ui` gets 401 before any page runs, so the `Host` and `X-Forwarded-Proto` it reads come from the core, which sets them. Only `GET /healthz` answers without the token, for probes; it shows nothing.

### Signing in

```mermaid
sequenceDiagram
  participant B as Browser
  participant U as UI
  participant C as Core AuthService
  B->>U: GET /login
  U->>C: GetLoginMethods(origin)
  C-->>U: passkey_registered, demo_sessions, demo_loading
  U-->>B: "Sign in with passkey", "View demo" only if demo_sessions, a loading notice if demo_loading
  B->>U: POST /login/passkey/begin
  U->>C: BeginLogin(origin)
  C-->>U: ceremony ID, request options JSON
  U-->>B: ceremony ID, options
  B->>B: parseRequestOptionsFromJSON, navigator.credentials.get
  B->>U: POST /login/passkey/finish (credential.toJSON())
  U->>C: FinishLogin(origin, ceremony ID, credential)
  C-->>U: session token, session
  U-->>B: Set-Cookie __Host-openfief_session, go to /
```

- **The origin.** The UI tells the core the origin the browser uses: the scheme the core's front door reports in `X-Forwarded-Proto`, then the `Host` the core passed on. The core checks it against its allow-list (`OPENFIEF_AUTH_ORIGINS`), and its host is the relying party ID.
- **The cookie.** `__Host-openfief_session`: `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/`, expiring when the session does. The `__Host-` prefix makes the browser refuse it from any other host and with any `Domain`. Browsers treat `http://localhost` as a secure context and keep `Secure` cookies there, so the same cookie works through `kubectl port-forward`, and D-85 keeps the prefix everywhere, `localhost` included. Chromium keeps it there, which the end-to-end suite checks; Safari's acceptance of it on `http://localhost` is still to verify, by hand, since no Safari runs in the suite. Only if Safari refuses it does D-85 allow a cookie without the prefix, on `localhost` alone, and that fallback is not built. On plain HTTP to any other host the browser drops the cookie, and the login page says sign-in needs HTTPS.
- **"View demo"** posts to `/login/demo`, which calls `CreateDemoSession` and stores the `read` session the same way. On a demo whose data is still loading (`demo_loading`: demo sessions on, no demo marker yet), the page shows "Demo data is loading" with a *Refresh* button in its place, so a visitor waits for the demo instead of signing in to an empty install.
- **Enrollment.** An enrollment link is `<origin>/enroll#code=<code>`. The code is in the fragment, which the browser never sends, so it never reaches a request line, a log or a `Referer`. The page's script, [webauthn.js](../../internal/views/ui/web/static/webauthn.js), reads it, removes it from the address bar and history, and posts it to `/enroll/begin`; the UI hands it to `BeginRegistration`. Registering from an enrollment code also signs the owner in. "Add a passkey on this host" on the settings page runs the same ceremony with the owner's session instead of a code.
- **Every page** first asks the core `WhoAmI` with the cookie's session. No cookie, or a session the core no longer knows (`UNAUTHENTICATED`), drops the cookie and sends the browser to `/login`; an htmx request gets `HX-Redirect` instead. A read-scoped session gets 403 on the owner's pages before the UI calls the core.
- **Logout** revokes the session with `Logout` and drops the cookie, also when the core can't be reached. Dropping the cookie, on sign-out and whenever the core rejects the session, also answers with `Clear-Site-Data: "storage"`, so the browser deletes what the origin keeps, the service worker and its cache among it (D-151). htmx's history cache is off (`historyCacheSize` 0, with `refreshOnHistoryMiss`), so no snapshot of a page that was pushed into the history stays in `sessionStorage`. *Sign out everywhere* on the settings page posts to `/logout` too, with `everywhere=yes`, so the service worker empties its cache the same way; the UI calls `SignOutEverywhere`, which revokes every session (D-183), and drops the cookie. Unlike a plain sign-out, a refusal or an outage is shown and the cookie kept, so the owner never believes the other sessions ended when they didn't.
- **Confirm with your passkey** (D-183). When the core refuses an action for want of a recent [passkey check](../glossary.md), with `FAILED_PRECONDITION` and the `PasskeyCheckRequired` detail, the settings page shows *Confirm with your passkey* above everything, with a form that holds the refused action's path and fields: creating a script token, issuing an enrollment link or removing a passkey. Its button runs the check in [webauthn.js](../../internal/views/ui/web/static/webauthn.js), through `/passkey-check/begin` and `/passkey-check/finish` (`BeginPasskeyCheck`, `FinishPasskeyCheck`), then posts the form again. "Add a passkey on this host" gets `passkeyCheck: true` from `/enroll/begin`, runs the check and begins again, so the owner sees the passkey prompt twice. Removing the passkey that signed this session in signs the browser out.

### Browser security

- **Security headers through the core.** The core adds its own to every answer it proxies from a view plugin, and to its own refusals there (D-184, `browserproxy.SecurityHeaders`): a second `Content-Security-Policy`, `default-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'`, next to the view's, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer`, replacing whatever the view said about those three. A browser enforces every policy an answer carries, so the UI's own stricter policy below stays in force whole, and a third-party view without one, or with a looser one, is held to the core's.
- **Content Security Policy.** Every response carries `default-src 'none'; script-src 'self'; style-src 'self'; font-src 'self'; img-src 'self'; connect-src 'self'; manifest-src 'self'; form-action 'self'; frame-ancestors 'none'; base-uri 'none'`. Nothing is inline: scripts and the stylesheet are files the UI serves, chart data travels in `data-chart` attributes, and htmx runs with `allowEval`, `allowScriptTags` and its injected indicator styles off. A test checks every template for inline scripts, styles and handlers.
- **CSRF.** Every request that isn't `GET`, `HEAD` or `OPTIONS`, a multipart upload too, must come from the UI's own origin: `Sec-Fetch-Site: same-origin` when the browser sends that header, otherwise an `Origin` equal to the UI's origin. A request with neither is refused with 403 before any handler runs. `SameSite=Strict` on the cookie is a second line.
- **Other headers.** `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Cross-Origin-Opener-Policy` and `Cross-Origin-Resource-Policy: same-origin`, a `Permissions-Policy` that allows passkeys for the UI only, `Strict-Transport-Security` on HTTPS, and `Cache-Control: no-store` on pages, which hold the owner's record.
- **Vendored libraries.** htmx 2.0.11 (0BSD, 52 kB) and Chart.js 4.5.1 (MIT, 209 kB, its license header kept) are copied byte for byte from their npm releases into `web/static/vendor` and served by the UI; a test pins their SHA-256. Chart.js was chosen over uPlot because it draws both charts, the allocation's bars and the value line, with tooltips and no extra stylesheet.

### The look

The pages follow the [design system](../dev/design-system.md) and take every color, font, size and radius from its [`tokens.css`](../../design/tokens.css). The UI serves the design system's files itself, from the Go package [`design`](../../design/design.go) that embeds them, under `/static/design/`: the tokens, the self-hosted fonts, the favicon and Kasztan's poses. Nothing comes from another host, and nothing is copied out of `design/`. Every page loads the fonts, then the tokens, then the UI's own [`style.css`](../../internal/views/ui/web/static/style.css), which uses only semantic tokens, so dark mode follows the reader's system setting (or `data-theme` on `<html>`) without a line of its own.

- **Components.** One primary button per view, secondary outlined buttons, a quiet underlined "Sign out" and destructive red "Remove" and "Revoke"; status pills that always carry a word; tables with a sunken header row and monospace, right-aligned figures that always show their currency (D-20), each row a card on a phone (below); a label above every field, help text under it and the unit inside amount fields.
- **Pills.** An account's valuation status (D-36) is a pill with the date it is *valued through* in monospace, and a *Revaluation pending* or *running* pill with a gold dot. A plugin's trust is one of D-87's four badges with the exact signer under it (see the installed plugins below).
- **Kasztan**, at most once per screen: on duty on the sign-in and enrollment pages; asleep in empty states (no accounts, no flagged balance assertions or price checks, no plugins); with the seal when a statement was imported; at the drawbridge on the error page and over flagged balance assertions, which need the owner.
- **Charts.** The series are vert, then or, kasztan, a grey and the vert tint (D-30's order in the design system): on the value chart the gross, net and liquidation lines in that order, on the performance chart the time-weighted return first and the model portfolio's backtest second; each allocation bar takes the next color. [app.js](../../internal/views/ui/web/static/app.js) reads the colors and fonts from the page's CSS custom properties when it draws, and redraws when the reader's color scheme changes.

### On a phone and as an app

The pages are laid out for a phone first and widen from there; at 360 px and up no page scrolls sideways.

- **The menu.** Below 640 px the navigation and the session's scope and "Sign out" fold behind a *Menu* button in the top bar, which opens them as a full-width list. The button is a plain `<button>` with `aria-expanded`; [layout.js](../../internal/views/ui/web/static/layout.js) toggles it, and Escape closes it.
- **Tables become cards.** Below 640 px each table row is a card, one line per cell: the column's header on the left, the value on the right. Amounts stay monospaced, right-aligned and with their currency (D-20). `layout.js` labels each cell with its column's header (`data-label`, shown by the stylesheet) and gives the table ARIA table roles, since a table laid out as blocks loses its meaning for some screen readers; it does the same for every table an htmx swap brings in.
- **Long identifiers wrap.** Monospaced figures don't break, but a signer's identity, such as a keyless signer's workflow URL with its issuer, can be longer than a phone is wide, so it wraps anywhere (`.mono.ident` in [style.css](../../internal/views/ui/web/static/style.css)) instead of pushing the page sideways; nothing is cut off.
- **Without JavaScript** the navigation stays open in the bar and wide tables scroll inside their own box, as before. `layout.js` loads in `<head>` without `defer`, so the page is marked as scripted before it first paints and the menu doesn't flash open.
- **Charts** take the width of their card and are shorter on a phone; Chart.js redraws them when the window changes size. **Forms** are one column, every field and button at least 44 px tall, and a form's buttons share the row. The top bar and the page keep clear of a phone's notch and rounded corners (`viewport-fit=cover` and the safe-area insets).

The UI is also an app the owner can install, a progressive web app:

- **The manifest**, [`/manifest.webmanifest`](../../internal/views/ui/pwa.go), names OpenFief, opens `/` in its own window (`display: standalone`, scope `/`), and takes its colors from [`tokens.css`](../../design/tokens.css) when the UI starts, so no color is written outside the tokens: the top bar's ground as the theme color and the page's ground behind the splash screen. Every page also sets `theme-color` for light and dark from the same tokens. The icons are the Seal, the design system's app icon, at 192 and 512 px, a maskable 512 px one and Apple's 180 px touch icon, generated by `task design:icons` ([Design system](../dev/design-system.md)). The CSP admits the UI's own manifest only (`manifest-src 'self'`); the service worker is a script, which `script-src 'self'` already covers.
- **The service worker**, `/sw.js`, is served at the root so its scope covers every page. The UI writes its configuration at the top of [sw.js](../../internal/views/ui/web/pwa/sw.js) when it starts: the exact list of files it may cache (every style, script, font, mark, icon and Kasztan pose under `/static/`, the manifest and the offline page) and a version, a hash of all of them, which names its one cache.
  - It **caches**: those files only, when it installs and again after a sign-in (`POST /login/passkey/finish`, `/login/demo`, `/enroll/finish`), and serves them from the cache. A listed file missing from the cache comes from the network and is not stored.
  - It **never caches** a page, an htmx fragment, a form's answer, the read API or anything else: those hold the owner's record and keep `Cache-Control: no-store`. A page always comes from the network; every other request passes through untouched.
  - **Offline**, a page the owner opens shows the static offline page, `/static/offline.html`: Kasztan asleep and one sentence, no data. The UI renders it once from the layout when it starts, with no session.
  - On **sign-out** (`POST /logout`) it empties its cache; a **new version**, any static file changed, installs a new worker, which drops the old cache when it takes over. The worker script and the manifest are `no-store`, so the browser sees a new version on the next page load.
- **Passkeys in the app.** The installed app is the same origin as the tab, so the relying party ID, the passkeys and the `__Host-` cookie are the same, and WebAuthn works in a standalone window in Chrome, Edge and Safari. Launching the app is a navigation the owner started, so the `SameSite=Strict` cookie goes with it. The limits: on iOS and iPadOS an app on the home screen keeps its own cookies apart from Safari, so the owner signs in once more inside the app (with the same passkey, synced by iCloud Keychain); an enrollment link opened from another app opens in the browser, not in the installed app, so a first passkey is made there; and a link into the UI from another site arrives without the `SameSite=Strict` cookie, as in a tab, and shows the sign-in page.

- **The Ask box** (D-194) understands a fixed set of commands and answers them from the read API alone, with the session's token; it holds no AI model and says so. The commands, matched by pure functions (`parseAsk`, case and closing punctuation aside): *what needs me* (also *inbox*, *todo*), answered with the open items; *show* an account, a sleeve or an instrument, by its name, ID, ticker or ISIN (`matchTarget`, exact first, then prefix, then substring; *show account …*, *sleeve …*, *instrument …* narrow it), answered with the account's largest holdings, the sleeve's accounts or the instrument's holdings and latest price; *why is … failing* (also *sync of …*), matched against the instances that synced (`matchInstance`, so *xtb* finds `xtb-main`), answered with its status and latest attempts, each with its error class and never its text (D-198); *allocation by* asset class, currency, institution (or broker) or sleeve; *performance* this year, this month, over the last 12 months, last year, in a year, since a date or since tracking began (`periodRange`), answered with the time-weighted return from the index's first to its last day; and *value* on an ISO or day.month.year date, today, yesterday or at the end of last month or last year. Each answer is a card (`answerCard`): a title, one sentence, a small table and one *Open …* link to the place it summarizes, the account, the Inbox, the allocation, the performance chart or the overview on that day; anything else gets the commands the box understands with an example of each. The answer shows as a conversation, the question in a bubble on the right and the card under it; the form asks `/ask` through htmx and works without it through the overview's `q`. The suggestion chips come from the current state (`askSuggestions`): what needs the owner while anything is open, why each failing sync fails, the first account and sleeve, the allocation by currency, this year's performance and the value at the end of last month. "/" focuses the box from anywhere but a field ([ask.js](../../internal/views/ui/web/static/ask.js)). The box changes nothing, and the question is never logged and never leaves the UI (GR-12): the UI logs a failed call by its method and code, the core's front door logs a path without its query (`TestProxyLogsNoQuery`), and the read API logs no path. `answerer` is the seam an agent can take over in M2 (P-57): it gets a question and gives a card; `commandAnswerer` is M0's.

A refusal, such as a lot never entered, shows the core's reason above the page (400); an unreachable connector does the same with 503. A read session sees neither the column nor the button.
- **Interest.** A transaction of the kind `TRANSACTION_KIND_INTEREST`, such as a bond's coupon (D-101), is listed with the kind *interest*, as every kind is written from its name.
- **The "Upload statement" form** appears to the owner only, on the page of an account whose one bound connector instance runs and declares statement files in its manifest: the UI asks the core's `StatementService.ListStatementAccounts`, its owner service (D-109, D-79), and shows the form only on the accounts it lists, naming the instance. It is a `multipart/form-data` form with the mode first, then the opening cash fields when shown, then the file. While the core says the account's next upload is opening, the account hasn't started, and the form asks **How the account starts** (D-136): *From the holdings of a current statement (opening)*, preselected, with **Cash at the start**, an amount and its currency, which the owner enters once for a statement that holds no cash balance, such as an XTB export's open positions; or *From a statement of its whole history (transactions)*. Once the account has started, the mode is preselected as `auto`, which sends no mode so the core chooses transactions, and the owner may override it with `opening` or `transactions`; no cash field is shown. The UI reads the body as a stream (`MultipartReader`), never parsing it into memory or onto disk: it checks the mode part and the cash fields after it (`opening_cash`, `opening_cash_currency`, at most 64 bytes each), then sends the core the header (origin, session, account, the browser's file name, mode, and the opening cash in upper case when an amount was entered) and the file in 64 KiB chunks as it reads them, through a client with a five-minute timeout (`uploadClient`). The body may be 64 MiB plus 64 KiB for the form (`http.MaxBytesReader`); past that, or when the body breaks off, the UI cancels the call so the core imports nothing, and answers 413 or 400. On success the page shows the import batch and its mode, its transactions (new, new versions, unchanged), its balance assertions and how many failed, the accounts a statement of several accounts was booked into, linked, the broker accounts no account is mapped to, with a link to the accounts page to map them, and the core's first 100 ingest problems with their kind, row and reason. A refusal, such as a file the connector can't read, shows the core's reason above the page (400, or 413 over the core's limit); a connector that can't be reached 503; a form without the mode first, with an unknown mode, an unknown field or without a file 400 without calling the core.
- **The first-run wizard** (D-73, D-191). The overview sends an owner session to `/setup?step=sleeves` while the install has no account, so the owner who just created the first passkey, which opens the overview, lands there; a read session gets the overview's empty state. A demo never shows the wizard: its data comes from the demo loader, and a wizard's sleeves or accounts written before the loader marks the database would make the loader refuse it as a real one. So on a demo the overview keeps an owner without accounts, saying "Demo data is loading" while it is, `/setup` redirects to `/`, and the core refuses the forms' writes until the demo marker exists ([Demo](../dev/demo.md)). The first step shows the three sleeves the install started with (D-71) and the kinds, with the same forms as `/sleeves`; the second the account forms of `/accounts`; the third Kasztan with the seal, links to the overview, Accounts and Sleeves, and that more plugins are installed with the `openfief` CLI (D-46). A numbered list of the steps, with the current one marked, links them in any order. Each form carries the page it returns to in `next`, which the UI accepts only for `/sleeves`, `/accounts` and the wizard's two form steps, so a form can't send the browser elsewhere.
- **The sleeve forms** leave every rule to the core. The role is "the kind's default", defensive or offensive, with a box for the owner's explicit choice of a role other than the kind's (D-71); a kind's default role is chosen once, when it is added. A refusal shows the core's reason above the forms, on the page the form was on.
- **The account forms** take the account's tax wrapper from the read API's settings, the pack's default first, and its sale fee rule (D-78) with the commission and conversion rates typed in percent (`0,29` or `0.29` is 0.29%, sent as `0.0029`) and the minimum with its currency; leaving the fee fields empty keeps an account's rule, or zero for a new one. They offer the broker accounts the connectors reported, unmapped ones only, as `instance/ID`, so the owner never types an account number (D-72): picking one also picks its connector instance, and an empty institution takes the broker account's. The connector instances offered are the installed plugins with the `connector` capability; when the core can't read its cluster, those it has seen in bindings and broker accounts, with a sentence saying so. An unmapped broker account gets "Create its account" and "Map to an account". The change form of an account at the treasury bond registry also has its [payout setting](../glossary.md) (D-135): "Stay as the account's cash" or "Paid out", sent as `bond_payout` with `UpdateAccount`, and a date field, "Change takes effect from", sent as `bond_payout_from`: empty is today, and an earlier day makes the next sync book the coupons and maturities from then anew (D-162); other accounts' forms don't offer them, and the core refuses a paid-out setting for them. The change forms are folded into `details` elements in each table row.
- **The installed plugins** (D-46, D-56) are a table: the instance, the capabilities its running version may use with those its manifest requests, a *Market data* pill on a market-data connector with the sentence that each sync tells it every instrument the owner holds and the model portfolio's targets, or a note that its manifest asks for that and the grant doesn't approve it yet (D-123), a *Bond terms*, *Index levels* or *Index readings* pill when the core stores what it delivers of them, or a note that they are dropped until the grant approves them (D-179, D-186), its trust as one of D-87's four badges, *Verified* (in the catalog and reviewed), *Yours* (one of the owner's signers), *Unreviewed* (signed by OpenFief's CI, by a catalog publisher or by another trusted signer, but not in the catalog) or *Blocked* (refused, not checked yet, or a trust the UI doesn't know), with the read API's signature trust in full, the signer and the operator's reason under it, and for an image refused as signed only by signers the owner doesn't trust, those signers with what to do: add the signer to the trusted signers if it is theirs, otherwise the image may be forged (D-169), the operator's `Ready` reason as its status, and the image digest. Read sessions see it too on `/plugins`, linked from the navigation, since no decision restricts it; the owner also sees it on the settings page. It has no form or button: plugins are installed, approved and removed with the `openfief` CLI (D-46). When the core can't read its cluster, the table is replaced by a sentence and the rest of the page still works.
- **A removed instance's transactions** (D-58) stay in an account's list. The new Source column names the connector instance each came from, or the source for anything else, and marks "removed instance" when no plugin of that name is installed, as the read API reports it.
- **The navigation** (D-192) has four places: Overview, Accounts, Inbox and Settings. `withSession` reads the open count of attention items with the settings, one more read API call per page, and the Inbox link shows it as a gold pill; a core that can't count them leaves the count out and logs why, and the page still renders. Settings opens on the general settings for the owner and on the sleeves for a read session, whose settings page is the owner's only; the sleeves and the installed plugins sit under it, behind a segmented *General · Sleeves · Plugins* switch, so every earlier page stays reachable. The overview's counts of attention items, flagged balance assertions and price checks and suggested transfers link the Inbox. A suggested transfer is an attention item, so the open count includes it.
- **Price checks** are grouped by instrument (`latestPerInstrument`): the latest by date, then by source, the earlier ones newest first. A flagged one's Inbox item shows the price holdings are valued at and the institution's own price side by side with the difference and the threshold, and its history behind a disclosure; the done view lists every instrument's. Holdings keep their valuation, and nothing in the UI changes a price. The owner gets an *Acknowledge* button on every flagged check not yet acknowledged, and a threshold field per instrument in percent: `fractionOf` turns "2.5" into "0.025" exactly, an empty field clears the instrument's own threshold, and anything but a percent greater than 0 and less than 100 is refused with 400 before the core is called. A relative difference is shown with `percent`, the decimal fraction times 100 exactly, every digit kept, such as `2.8232%`; a currency mismatch has none.
- **Instruments** are named by their display name (D-197), when they have one, before the ticker and ISIN: `Synthetic Fund · SYN (XX0000000001)` (`instrumentLabel`). An Inbox item about an instrument, such as a flagged price check, links its page, and so does the Inbox's notice after the owner confirms a ticker's ISIN; the Ask box's answer about an instrument opens its page.
- **Amounts** stay the read API's exact decimal strings, always with their currency (D-20): a balance assertion's reported and derived balances carry their ledger account's currency, except a holding's, which are quantities. Every page writes them in the number format (D-113) that `GetSettings` gives: `withSession` reads it after `WhoAmI` and puts it in the request, and each render binds the templates' `money`, `amount` and `balance` to it. Only the separators change, never the digits, sign or currency; a space separator is written as a narrow no-break space so an amount never wraps, which gives `5 000,00 PLN` by the Polish default. A share is computed with the kernel's `Decimal.Quo`, half-even to one decimal place. Each chart's data carries the format's two separators, and the chart script writes the value axis's ticks and the tooltips with them; it turns the strings into numbers only to place the marks and tick values, and its tooltips show the exact strings.
- **The number format and the marginal rate** are set on the settings page, read from and handed to the core's `SettingsService`: the formats the pack offers, each shown as `5 000,00` written in it, marked as the pack's default until the owner picks one, and the marginal PIT rate in percent (`32` is sent as `0.32`), which an IKZE's liquidation value needs. The core refuses a key it doesn't offer or a rate outside 0 to 1, and the page shows its reason.

### The demo

[`deploy/demo/plugins/ui.yaml`](../../deploy/demo/plugins/ui.yaml) installs the instance `ui` with a grant for exactly the `view` capability and the browser path `/`. The operator runs it as Service `plugin-ui`, port `connect` (8080), which only the core may reach. The demo's Ingress, [`deploy/demo/routes/openfief.yaml`](../../deploy/demo/routes/openfief.yaml), sends every path to the core, Service `openfief-core`, port `http`, which serves the read API itself and proxies the rest to the UI; the demo-only `core-from-traefik` policy admits k3s's Traefik to the core, and nothing admits it to the UI. The core's other Connect services, the AuthService and the owner's entry services, are on its plugin port, `connect`, which only plugin pods reach: neither the Ingress nor `kubectl port-forward` to `http` gets to them (D-115). The demo's core accepts `https://demo.openfief.dev` next to the base's `http://localhost:8080` (`OPENFIEF_AUTH_ORIGINS`), and runs with `--demo-sessions`, so "View demo" works on the demo database.

## Decisions

- **GR-12**: a failed core call is logged by its Connect code, and a page that can't render or a response that can't be written by `kernel.LogSafe`, never by the error's text.
- **D-3** makes the UI the default view; **D-6** says it reads through the public API like any view. `TestReadsOnlyThroughPublicAPI` keeps the package from importing anything of OpenFief's but the kernel and the SDK.
- **D-26** and **D-60**: passkeys only, per host, the first through a one-time link. **D-27**: the UI authenticates as a plugin with its projected token.
- **D-28**, **D-81**: the UI is a ClusterIP Service that only the core calls; a route, a port-forward or the demo's Ingress reaches the core, which proxies the UI's browser path. Which browser path the UI takes is the narrowest that works with the core's own paths: `/`, so the UI's pages keep their paths and enrollment links stay `<origin>/enroll#code=...`.
- **D-84**: no fixed token: the UI only ever presents its projected token, and is developed against kind or k3d.
- **D-85**: the `__Host-` cookie everywhere, `localhost` included; Safari on `http://localhost` is still to verify (above).
- **D-193**: the overview's order and places, the status sentence, the value card, one chart card and the accounts by sleeve. The allocation is the chart card's third tab, as bars with their switches; the change this month counted from the last valued day before the month, the year's return from the last valued day before the year, a sleeve's total as its accounts' gross values with cash, and an account's pill's order are the UI's readings. **D-194**: the Ask box and its commands, read only, the question neither logged nor sent anywhere; the phrasings each command accepts, matching names by exact, prefix then substring, and answering on the overview without htmx are the UI's readings. **D-195**: the total links to its accounts, an account row to its account, a holding to its instrument, an allocation bar to the accounts or holdings behind it, and an instrument has its own page. The UI's readings: the account page's tabs and their order follow the design system's M0 screens; an instrument's prices are drawn for the last year; the holdings behind an asset class or currency bar are a page of their own (`/holdings`), since no read API call filters holdings by group; the breadcrumb goes through the account an instrument was opened from.
- **D-30**, **D-36**, **D-62**: the three charts, the valuation status per account, the reporting currency. **D-106**: value and performance are separate charts, and totals include cash. **D-77**, **D-78**, **D-91**, **D-113**: three values side by side with a switch on each money chart, the owner's fee rules and marginal rate, the no-longer-updated mark, the number format.
- **D-105**: the owner confirms or rejects each suggested transfer in the Inbox, and the UI hands each decision to the core's `TransferService`. Offering a rejection of a confirmed pair and a confirmation of a rejected one, as corrections, and counting the suggestions in the performance card are the UI's readings.
- **D-130**, **D-131**, **D-192**, **D-196**: the attention items in one place, the Inbox, grouped by what the owner does about them, with acknowledged and done items behind their own views, the open count in the navigation and on the overview, and an account's own items at the top of its page; no check has a page of its own, so the old pages redirect to the Inbox. An item one field or button settles is settled in place: confirming an ISIN, acknowledging a price check or an item, confirming, rejecting or correcting a transfer, mapping a broker account, retrying a sync. The UI's readings: a gold pill for the count; links to each account an item is tied to and to the instrument it is about; the done view also lists the decided transfers and every price check, so nothing the removed pages showed is lost; a read session's Settings link opens the sleeves.
- **D-22**, **D-110**, **D-112**: the price checks, the latest per instrument with its history, in the Inbox: a flagged one as an item, every one in the done view; the owner acknowledges a flagged check and sets an instrument's threshold there. Where they show, counting instruments whose latest check is open on the overview, and acknowledging only flagged checks, are the UI's readings.
- **D-9**, **D-49**: the owner enters bond lots on a bond account's page, and the UI hands each to the core's `BondLotService`, a contract for view plugins shaped like the `ModelPortfolioService`, which the core hands to the right connector. Which accounts get the form is the UI's narrow reading: the institution `treasury-bonds`, the one the treasury-bonds connector delivers under.
- **D-7**, **D-49**, **D-109**: the owner uploads a statement on the page of an account whose connector takes files, as the core's `StatementService` says, and the UI streams it to the core, which hands it to the connector bound to the account and chooses the mode unless the owner overrides it.
- **D-46**, **D-56**, **D-87**: the UI only shows the installed plugins and their signature trust, grouped into four badges; nothing in it installs, approves or removes one. **D-58**: transactions from a removed instance are marked, not hidden.
- **D-52**: while the model portfolio is off, the UI shows none of it; the owner turns it on and enters it on the settings page, which hands it to the core through the `ModelPortfolioService`, a contract for view plugins next to the AuthService. **D-53**, **D-54**: its backtest as the second line from the charts' start and its drawdowns. **D-138**: every time chart starts on a date the owner can choose, the portfolio's by default where tracking began, which it marks, an account's on its first day; keeping the choice in the URL rather than a setting is the UI's reading (implementation question 56). **D-61**: the value-over-time line is the time-weighted return.
- **Where Kasztan stands** is the UI's reading of the design system: the error page and the flagged balance assertions get the drawbridge, as things that need the owner; a finished statement import gets the seal. *Unreviewed* covers OpenFief's CI and catalog publishers too when the version is not in the catalog, as D-87's wording reads.
- **Rates are typed in percent.** D-78's fee rule and marginal rate are fractions in the core's contracts; the forms take percent, as statements and tax forms write them, and accept a decimal comma.
- **Every request reads the settings.** The number format can change from another tab, so each page asks `GetSettings` rather than caching it; it is one small read API call.
- **The cookie is `Secure` on `http://localhost` too.** The AuthService contract says the cookie is Secure except on `http://localhost`. A `__Host-` cookie must be `Secure`, `gosec` (G124) refuses an insecure cookie, and current Chrome and Firefox keep `Secure` cookies on `localhost` as a secure context, so the UI sets one cookie everywhere. Safari's support for that is still to verify; D-85 keeps the `__Host-` cookie everywhere and falls back on `localhost` alone only if Safari refuses it.
- **The origin comes from `X-Forwarded-Proto` and `Host`, as the core sets them.** Only the core reaches the pod, with its token. The core takes the scheme from TLS or from the owner's Ingress in front of it, and checks every origin against its allow-list, so a forged value can't use a passkey or session made for another host.
